### Fixed — ML serving reads the rows training learnt from, rates `unknown` without a baseline, and keeps slots after midnight

**Serving rows.** The ml-service built inference features from
`status = 'OPERATING'` rows on days with no schedule or an `OPERATING` one.
Training (`db.fetch_training_data`) also keeps `UNKNOWN`-schedule days and any
status with a wait of at least 5 minutes, so the lags and rolling averages at
inference came from a smaller population than the model learnt on.
`_SERVING_QUEUE_FILTER` now uses training's filter. Training's park-wide
operating-day heuristic on no-schedule and `UNKNOWN` days is not ported. It would
scan every ride of the park on each request, and a day on which the ride posted a
wait of 5 minutes or more passes it in practice.

**No baseline means `unknown`.** Without a typical-day-peak or P50 baseline,
`predict_wait_times` rated against the ride's own `rolling_avg_7d`, which is a
different scale from the park path, and fell back to `moderate` when that was
missing too. It now answers `crowdLevel: "unknown"` with `baseline: 0`, so the
PCN and Chronos re-tiering, which only runs when `baseline > 0`, leaves it alone.
`getAttractionPredictions` now sends the park's `p50Baseline` and
`typicalDayPeakBaseline`, as the park path already did, so a single ride is
rated the same way as on its park. `wait_time_predictions.crowdLevel` stores
`unknown` as NULL instead of adding an enum label, because a new label would make
`synchronize` rebuild the type on that table. Reads map NULL back to `unknown`.

**Windows past midnight.** On a day that runs from 10:00 to 01:00, the 15-minute
slots between 00:00 and 00:45 carry the next local date. They were joined to that
date's window, which opens at 10:00, and dropped as closed. That happened in
`predict.apply_schedule_features`, in `schedule_filter` and in training's
`features.add_park_schedule_features`. All three now also check each slot against
the previous date's window. In training, `time_since_park_open_mins` for those
slots counts from the opening of the window the slot falls in.

**Training triggers.** nf-service and pcn-service `/train` now write
`is_training: true` before they launch the runner. Until now only the runner
wrote it, once its imports had finished, so a second `/train` sent in that gap
started a second run. If the launch fails, the lock is released.
ml-service `/train` rejects an unsafe `version` with a 400. gunicorn's
`pre_fork` now refreshes the master's model from the sentinel, so a worker that
gunicorn recycles after a retrain starts on the active model.
