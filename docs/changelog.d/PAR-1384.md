### Fixed — Parky's day tip is kept under the days it reads, counts from the park's today and is read by the chat itself

The tip's sentence can name a quieter neighbouring day ("lieber Freitag"), but its Redis key held
only the chosen day's level. Once the forecast moved Saturday from low to high, the kept Friday tip
still sent visitors to Saturday for up to twelve hours. The key is now
`parky-tip:v3:{parkId}:{today}:{date}:{days}:{locale}`, where `{days}` is a digest of each day the
prompt reads: its date, status and crowd level, and on today the level so far (`daysDigest`).
Weather stays out, since every forecast run moves it. `servedVerdicts`, which the display check
reads, builds the same key.

The route takes an optional `today`, the park's today as park.fan's relay keys its cache by it. One
that is not the park's answers 204 with `no-store` and writes nothing; before, a request with
tomorrow's date at 23:58 stored today's "morgen …" under tomorrow's URL at the frontend's CDN. The
other 204s leave with `public, max-age=300, s-maxage=300` (`TIP_NONE_CACHE_CONTROL`): a spent
budget or a failed call passes within the day, so the frontend keeps them minutes instead of until
the next ring.

Today's line in the prompt carries the level measured so far ("so far today: very low"), the
„bisher" the day dialog shows under the forecast, and a tip for today says both where they differ
instead of "lieber nicht" over a quiet morning (prompt version 3).

The chat opened from a tapped tip no longer hands Parky the browser's `dayTip.text` as his own
words, which he would defend even if it was forged. `ParkyTipService.dayTip` reads the sentence it
serves now in the chat's language, through the same cache, and the day's facts from one calendar
read; the field stays accepted and unused. Where no tip is served now, Parky gets the facts and is
told not to stand by the quoted sentence
([Parky's tip](frontend/assistant.md#parkys-tip-for-a-calendar-day)).
