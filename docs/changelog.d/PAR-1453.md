### Added — every attraction can carry a kind without hand work, and `GAME` is one

`attractionKind` was empty almost everywhere (Phantasialand 0 of 40, Hansa-Park 0 of 83,
Magic Kingdom 0 of 38): it was only ever typed by an editor, plus the maze rule's `MAZE`,
and nothing derived it. Clients could not tell a ride from a show and guessed; the app
called anything that posted a wait a ride, which files Magic Kingdom's PhilharMagic, Hall
of Presidents and Laugh Floor as rides.

A new column, `derived_attraction_kind`, is rewritten nightly by `detect-seasonal` from the
ride profile's glossary type ids, then a published minimum height, then (for non-headliners
only) the name. The API serves the editor's `attraction_kind` first and says which one it
served in the new `attractionKindSource` (`curated` / `derived`), so a better rule replaces
every derived value and never a curated one. Queues are deliberately not evidence. On the
payloads of 2026-11-27 the rule files 33 of Phantasialand's 40 rides and 25 of Magic
Kingdom's 38; the rest stay null.

`GAME` (midway game, arcade, shooting gallery) joins the enum, in the admin editor's
dropdown and Swagger. Clients that do not know it read it as unknown: the web's badges
test for single values, the app's parser falls back to `unknown`.

The admin data-quality report (and the MCP `data_quality` tool) lists parks with live rides
that carry no kind at all (`attractionsWithoutKind`). The column appears on the next deploy
through `synchronize`; it fills on the next `detect-seasonal` run (02:30) or when that job
is triggered by hand. See [attraction kind](frontend/attraction-kind.md).
