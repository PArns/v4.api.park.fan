### Added — the admin sees the derived attraction kind, and MCP reads paid queue products and the app's news export

The admin's ride list (`GET /v1/admin/content/parks/:id/attractions`) sent only the editor's
`attraction_kind`, so park.fan's editor asked the public park payload for the kind the rule had
derived. Each ride now carries `derivedAttractionKind` and `attractionKindSource` (`curated`,
`derived` or null) beside the raw column, and the ride editor's `attractionKind` field serves the
derived kind as its `resolvedValue` where no editor chose one; its hint no longer says a kind
cannot be derived. The data-quality report's `attractionsWithoutKind` adds `withoutKindRefs`
(`{ id, name, slug }` per ride) beside the names, so a client stops matching rows by name; the
names stay. See [attraction kind](frontend/attraction-kind.md#in-the-admin).

The admin MCP server gains three tools. `park_purchases` lists a park's paid queue products per
park-local day (Lightning Lane Multi Pass, Premier Pass, one ride's Lightning Lane) from the
schedule rows `/schedule` serves, with price, sold-out state and the ride a per-ride product is
for. `news_export_status` and `run_news_export` ask park.fan's new `/api/news-export/status` and
`/api/news-export/run` with the revalidation secret: how far the app's export on media.park.fan
lags the site, and a new run of `publish-media.yml` (editor, dry run by default, audited
`news-export.run`). `curate_park_attractions` takes `adoptDerivedKind` to make a ride's derived
kind the editor's, and the curation tools say that `attractionKind` takes `GAME` and that null
hands a ride back to the rule. `data_quality` passes the refs and drops the bare names. See
[admin MCP](admin/mcp.md#paid-queue-products).
