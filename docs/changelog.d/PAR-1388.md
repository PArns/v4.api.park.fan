### Fixed — Parky's day tip reads whole calendar months, keeps today's level so far to today's tip, and the chat only reads it

The tip read its days as the date ± 3 days. `buildCalendarResponse` keeps only whole months
(`calendar:month:v2`), so whenever the month was not cached, such as the current month past its two
warm hours, that week was built from the database on every tip request and kept nowhere. The tip
now asks for the whole month or two holding the window and cuts it to the same days after the read
(`daysAround`): a cached month costs one `MGET`, a missing one is built once and kept for the next
tip and the grid.

Today's level so far (`todayCrowdLevel`) was in the input and the key of every tip whose window
holds today, so each move of it had up to four dates written again in six languages. Only the tip
for today itself reads it now (`soFarToday`, used by both the prompt and `daysDigest`); prompt
version 4. The tip for today carries that level in its payload (`todayCrowdLevel`, optional, absent
on other days and before today has one), so park.fan hides a sentence that says another morning
than the „bisher heute" beside it.

A chat opened from a tapped tip ran `ParkyTipService.dayTip` through the tip's cache with a write on
a miss: the question waited for a model call (20 seconds' timeout, one retry), spent budget, and
could hand Parky a sentence the visitor never saw, which the prompt then called a moved forecast.
`dayTip` now only reads the kept tip (`readCachedJson`, also used by `cachedJson`). Without one,
Parky gets the facts and is told he cannot see the tip the visitor was shown, so he neither stands
by nor takes back the quoted sentence; "your forecast has moved since" stays for a kept tip whose
sentence differs from the quoted one
([Parky's tip](frontend/assistant.md#parkys-tip-for-a-calendar-day)).
