### Added — rotating a data API key, with a grace period for the old secret

A data key whose secret leaked, or whose holder changes hands, can now get a
new secret without being reissued ([rotation](frontend/api-keys.md#rotation)).
`POST /v1/admin/api-keys/:id/rotate { graceHours }` (owner only, 0 to 720
hours) answers the new key once, in the shape a create does; name, usage,
allowance, parks, end date and statistics stay. The old secret keeps working
for the grace period, so the holder can deploy the new one without an outage,
or stops at once with 0; a second rotation during a grace replaces the secret
it kept. `DELETE /v1/admin/api-keys/:id/previous` ends a grace now. A revoked
or expired key is a 409.

The old secret's cached lookup lives five minutes at most and never past the
end of its grace, which it also carries and compares on every read, so the
cache cannot stretch the grace by a second. Each secret records its own last
use: a rotation starts the new one's `last_used_at` at null, so the admin list
shows whether anyone has switched while the old one's goes on counting. Audited
as `api-key.rotate` (with `graceHours`) and `api-key.previous.revoke`, with
prefixes and dates, never a secret; no hash is in any answer.

Schema: four nullable columns on `api_keys`, added by `synchronize` at the next
boot with nothing to backfill ([the entities are the schema](rules/the-entities-are-the-schema.md)):
`previous_key_hash`, `previous_key_expires_at`, `previous_last_used_at` and
`rotated_at`. A key that was never rotated has them null and behaves as before.
