### Added — Google Search Console in the admin: queries, pages and clicks from Google, next to our own traffic

New module `src/search-console/`. A Google service account (`GSC_SERVICE_ACCOUNT_JSON`, raw or base64,
and `GSC_SITE_URL`, e.g. `sc-domain:park.fan`) reads Search Console's `searchAnalytics.query`; without
both the module is off and `status.configured` is false. A small client over `fetch` and Node's
`crypto` (the service account's RS256 JWT, an access token kept until a minute before it expires)
replaces `googleapis` (about 245 MB unpacked) and `google-auth-library`: no new dependency. The
Bull queue `search-console` imports nightly at 09:20 UTC and on demand: the last `GSC_IMPORT_DAYS`
days (default 3, Google finalises late) again and every day of the last 16 months never fetched, so the
first run is the backfill. Per day, rows by page, query, country and device, and rows without the query
that carry the property's own totals (Google leaves anonymised queries out of the first kind).
`search_console_rows` is a hypertable (30-day chunks, compressed after 35 days, one segment per batch,
chunks dropped past 500 days by the nightly job under a 5 s `lock_timeout`). A day imported again is a
new batch in `search_console_batches` and the reports read only the newest batch of each day, so a
re-import does no UPDATE or DELETE; a day that did not change writes nothing. Page URLs become the
site statistic's paths (origin, query and trailing slash dropped, lower case; `www` and `http` forms
merged; other subdomains skipped) so they join `site_pageviews`.

Admin endpoints under `/v1/admin/search-console`: `GET status`, `POST import` (editor, audited,
`202 { queued: true }`), `GET queries`, `GET pages` (with the site's own visits, bounce rate and visit
length from the `search` channel per path) and `GET series` (day, week, month), with the site
statistic's `days`/`from`/`to`/`locale` window, a change against the window before, and `ctr` and
`position` computed on read (`position` is null without impressions). The MCP tools `gsc_status`,
`gsc_queries`, `gsc_pages` and `gsc_series` return queries, paths and Google's error text under
`visitorData`. New variables `GSC_SERVICE_ACCOUNT_JSON`, `GSC_SITE_URL`, `GSC_IMPORT_DAYS`. Setup:
[Search Console setup](admin/search-console-setup.md); the contract:
[Search Console](frontend/search-console.md).

### Fixed — Search Console totals were about a third of Google's

Google drops the traffic of anonymised queries as soon as a page is combined with a country or a
device, and the import took its totals from a `page, country, device` download. The import now stores
five levels per day from five requests: the property (no dimension, the totals the Search Console chart
shows), `page`, `country` and `device` alone (complete), and the `page, query, country, device` rows.
Totals, `previous` and series come from the property rows, the pages list from the page rows (their sum
is a little above the property's, as in Search Console's Pages table), and under a `country` or `device`
filter the totals and series come from the complete country or device rows while the pages list comes
from the visible queries and the response carries `partialBreakdown: true`. New column
`search_console_batches.format` (integer, default 1, no table rewrite): every stored day counts as not
fetched in the new format, so the first run after the deploy imports the 480 days again (five requests
a day). Until a day is re-imported the reports skip it. Only new field in the responses: optional
`partialBreakdown`.

### Changed — Search Console's `days` ends at the last day with data

A rolling window (`days`, or none given) on `queries`, `pages`, `series` and the `gsc_*` MCP tools used to
end today, so with Google's lag of two or three days "28 days" held about 25 days of data. It now ends at
the last day with data and starts `days - 1` before it, the way Search Console's "last 28 days" counts;
`previous` is the `days` right before it. The echoed `from`/`to` are that window, and the `pages` report's
site figures cover it as well. A fixed `from`/`to` stays as asked, and without any data the window ends
today as before. No new field.

### Added — Search Console: image, news and Discover, and a URL inspection tool

The import now fetches the search types `image`, `news` and `discover` besides `web`. Each (day, type)
has its own current batch: new column `search_console_batches.search_type` (`varchar(10) NOT NULL
DEFAULT 'web'`) and `search_console_rows.search_type` (`varchar(10)`, nullable, `DEFAULT 'web'`, the
form a compressed hypertable accepts; reports read rows by `batch_id` and never filter on it), so
every stored day stays `web` and nothing is re-imported. Web, image and news take five requests a day
(property, page, country, device, query), Discover two (page and country: no queries, no devices, and
no property request, since Google has no `byProperty` aggregation for it: the property row is the sum
of the page rows): up to 17 a day. The first run after the deploy backfills the three new types over
480 days, about 5,760 requests; the client now spaces requests at least 100 ms apart (10 a second).
`GET status` gains `types` (coverage and rows per type); `queries`, `pages` and `series` and the
`gsc_queries`, `gsc_pages` and `gsc_series` tools take `type` (`web` by default, so every existing
response is unchanged); `queries` and any report that needs query rows answer 400 for `discover`; the
`site` figures of `pages` are `null` for other types.

New MCP tool `gsc_inspect_url`: Google's URL Inspection API (same service account and
`webmasters.readonly` scope, no new setup) for up to ten park.fan paths or URLs: verdict, coverage,
indexing, robots.txt and fetch state, last crawl, Google's and the page's canonical, sitemap, referrers,
mobile usability and rich results. Answers are cached for six hours, a Redis counter per Pacific day
refuses past 1,800 inspections (Google's limit is 2,000), and Google's text comes back under
`visitorData`. See [Search Console](frontend/search-console.md#search-types).

### Fixed — Search Console: an empty day in the old layout was asked for every night

A day with no rows whose batch was still in the older layout counted as unchanged and was never written
again, so every nightly run fetched it again. It is now written once in the current layout.

### Fixed — Search Console: the Discover import failed on every day

Google refuses to group Discover by device (400 `Requests for Discover cannot be grouped by device`),
and the import asked for it on every Discover day. No Discover day was stored, and since Discover's
backfill is the only work left after web, image and news, each run stopped after three failed days in a
row with that message as `lastError`. The import now asks Discover for `page` and `country` only, and a
`device` filter with `type=discover` answers 400 instead of zeros. Web, image and news are unaffected.
