### Fixed — CatBoost serving reads the park closed after hours, and a year-ago weekday beyond 28 days

Three follow-ups to the CatBoost train/serve parity work (PAR-1030/1040), in
`ml-service`:

- **`is_park_open` after close.** On a day with a published window, serving
  turned `status` to CLOSED before opening and after close but kept
  `is_park_open = 1`, its "assume open" default; training reads 0 there. Both
  read 0 now (`test_is_park_open_outside_hours_on_an_operating_day_agrees`).
- **`avg_wait_same_dow_4w` more than 28 days ahead.** None of the four weekly
  lags exists yet for such a row, so serving fell back to today's
  `rolling_avg_7d` for the whole far calendar. It now reads the same weekday and
  hour 52 weeks before the row — only for a ride with a reading at least 330
  days before base time (the `MIN_OBSERVED_DAYS` rule) and only where that slot
  holds a reading; anything else keeps `rolling_avg_7d`. One extra query per
  request, only for the keys it needs (the nightly daily batch; hourly
  requests never reach it). The origin hold-out's 61-day lead reads the same
  rule. No retrain: the trained feature is unchanged. With history starting
  2025-12-24 the gate opens around **2026-11-19**; until then every row keeps
  the fallback.
- **Curated ride type, behind `CATBOOST_CURATED_RIDE_TYPE` (default off).**
  `indoor_outdoor` and `attraction_kind` overrule the name regexes for
  `is_indoor` / `is_coaster` / `is_water_ride` where set; null keeps the regex.
  The flag is read by training and stored in the model metadata, and serving
  follows the active model, so flipping it takes effect with the next
  training. Each training logs the curated coverage among the trained rides.
  Serving's duplicate of `add_attraction_type_features` is removed.

Also documented, not built: an hourly observed-weather table from the
Open-Meteo archive (`docs/architecture/weather.md`).
