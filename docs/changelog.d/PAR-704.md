### Fixed — merging a ride no longer leaves its percentile buckets under an id nothing can re-derive

`queue_data_aggregates.id` is `md5("attractionId" || '|' || hour)`, and the primary
key is `(id, hour)`. That is what makes the key enforce one row per bucket and lets
the nightly `ON CONFLICT (id, hour)` fire at all. The attraction merge moved the
loser's buckets with the generic `move`, which rewrites one column — so the row
landed on the survivor still carrying a hash of the loser's id. No writer can form
that conflict target, and the next run over the hour inserted a SECOND row for the
same `("attractionId", hour)`. Readers `SUM("sampleCount")` and take
`percentile_cont` across the rows of an hour, so such a pair does not blur a figure,
it doubles it.

Measured against production on 2026-10-05: 4,029 rows with `hour` on or after
2026-06-05 — the day the deterministic id went live — carried a hash of some other
id, on 56 rides in 7 parks. 2,473 of them were already sitting beside the correctly
keyed row they collide with, both written in the same nightly transaction, which is
the counter-check: one INSERT cannot derive two ids for one `("attractionId", hour)`.

`queue_data_aggregates` is now a `custom` entry on `ATTRACTION_DEPENDENCIES`
(`moveAggregateBuckets`), because the row names the attraction twice — in the column
and inside the key. It drops the loser's buckets for hours the survivor already
holds, collapses the loser's own duplicate buckets to one row per hour, and then
reparents the rest with the id recomputed from `aggregateIdSql`, the one expression
the rollup also reads. `move` rather than `discard`: nothing recomputes a dropped
bucket on its own — `calculate-percentiles` only writes `[yesterday, today)` and
`backfill-percentiles` is triggered by hand over a bounded window — so discarding
would be a permanent hole in the survivor's history.

The park-side entry stays a plain `move`: `parkId` appears in neither half of the
hash. No schema change, and the existing rows are left as they are — the 2,473 with
a correctly keyed twin cannot be repaired by an UPDATE at all (the right id is
taken) and belong to `dedupe-percentile-aggregates`, and the rest sit in compressed
chunks that no scheduled job writes again.
