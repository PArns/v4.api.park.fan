### Added — An admin MCP server, with an OAuth 2.1 login and personal access tokens

`https://api.park.fan/v1/mcp` lets Claude Code, claude.ai or any MCP client read the admin's data
through 24 read-only tools: parks and rides with their live state, page views, the site
statistic (overview, breakdowns with filters, events, crosstabs, the search report) and its SEO
reports (landing pages, trends, not-found paths, uncovered pages), system and ML health, job
queues, data-quality findings, duplicate and retirement candidates, outage events and the audit
log. `claude mcp add --transport http parkfan-admin https://api.park.fan/v1/mcp`, then
`/mcp`, opens park.fan's consent page behind the existing admin login; a personal access token
(`pfa_…`, created on the account page) works without the login.

The authorization server is new: discovery under `/.well-known/oauth-*`, dynamic client
registration, PKCE with S256 only, single-use 60-second codes, one-hour access tokens and rotating
30-day refresh tokens whose reuse revokes the grant. Tokens are stored as SHA-256 in the new
`admin_api_tokens` and `admin_api_token_secrets` tables, capped at `viewer`, accepted by `/v1/mcp`
and by no other endpoint, and cut off with the account's sessions: deactivation, a password change
or reset, a second-factor reset and *sign out everywhere* now revoke them too. Redirect URIs are
loopback or https on `OAUTH_REDIRECT_HOSTS` (claude.ai and claude.com by default). New variables:
`API_PUBLIC_URL`, `FRONTEND_URL`, `OAUTH_REDIRECT_HOSTS`, `OAUTH_REDIRECT_PATHS` (only
`/api/mcp/auth_callback` on those hosts by default). Statistic values that visitors' browsers sent
come back under `visitorData`, labelled as data and never instructions. A Cloudflare rule in front of the API has
to let `/v1/mcp`, `/v1/oauth/*` and `/.well-known/oauth-*` through without a challenge. See
[admin MCP](admin/mcp.md).

### Changed — the admin MCP tools fold small values of the site statistic into `(other)`

The reports and the admin UI show every number; the MCP tools no longer do. In every list of the
statistic's tools (`analytics_breakdown`, `analytics_events`, `analytics_event`, `analytics_live`,
`search_report`, `seo_landing_pages`, `seo_trends`, `seo_not_found`, `page_views`) a row counted fewer than 5
times (its visitors when it has them, else its views, visits or events) goes into one `(other)` row at the end:
the counts, exits and the previous window's count are added up, everything else (bounce rate, averages,
durations, rates, a page type, an entity's id, sources) is `null`, and a row that is already `(other)`, the
values past the day's guard, joins it. The two crosstabs fold a side value whose cells add up to under 5 the
same way and leave every cell below 5 `null` in `counts`, with how many there are and their sum under `other`.
Totals are not folded. A series under a filter or a language, or per event or search surface, has its values
from 1 to 4 (and the rates computed from them) as `null` with `smallValuesHidden` saying whether any were;
a series of the whole site's totals is as counted. `seo_uncovered` (no counts), the `gsc_*` tools and
`audit_log` are unchanged, the strings still come back under `visitorData`, and each description tells the
model. One helper, `foldSmallRows` in `src/mcp/tools/small-cells.ts`, does the folding, with the limit in
one constant, `MCP_MIN_CELL`. The tools' echo of the window gains `hourlyFrom`
([retention](frontend/site-analytics.md#retention)). See [admin MCP](admin/mcp.md#small-values).
