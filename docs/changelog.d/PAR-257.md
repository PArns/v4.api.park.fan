### Changed — a changelog entry is a file of its own until the release folds it in

Every entry went directly under `## [Unreleased]` in `docs/changelog.md`, which
made that one line the busiest in the repository: two pull requests open at the
same time always touched it, and git conflicted there whatever their code did.
On 2026-09-15 and 2026-09-16 seven merges were sent back for a rebase and not
one of them had a conflict outside that file — PAR-146 twice in three hours,
PAR-160, PAR-171, PAR-215, PAR-232 and PAR-134. The cost was never the
resolution; it was the run that had to claim the issue again, install, and drive
the whole check chain a second time for a markdown merge.

An entry now goes to `docs/changelog.d/PAR-<issue>.md`. Two pull requests write
two files, so there is nothing to merge. `pnpm changelog:merge` folds them back
under `## [Unreleased]`, newest issue number first, and deletes them;
`pnpm changelog:check` says what it can read. The entries already in
`docs/changelog.md` are carried through unchanged — the merge inserts text and
never rewrites what is below the heading.

Measured against `main` = `81a6116` with `git merge-tree --write-tree`: two
branches that each add an entry the old way collide in `docs/changelog.md`, the
same two adding a fragment each merge clean.

The frontend has the same shape and not the same pressure. Over the 14 days to
2026-09-16, 30 commits touched `docs/changelog.md` here and 5 touched the
frontend's, so it keeps the single file until that ratio changes.
