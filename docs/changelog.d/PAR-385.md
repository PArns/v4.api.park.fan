### Added — `hasVirtualLine`, and the `VIRTUAL_QUEUE` branch that never existed

A ride with a virtual line had no way of saying so. Efteling's Danse Macabre
runs one and its page showed CLOSED and a single-rider badge, because a virtual
queue that is handing out nothing at this moment publishes no queue at all —
there is nothing in `queues` to read it off, and reading it off `queues` is the
mistake `has_single_rider` was written to avoid in the first place.

So `has_virtual_line` is the same kind of column and for the same reason: a
static fact about the ride, nullable, written by hand and by no sync. Null stays
"nobody looked" rather than "no", which is what keeps the ride page from
publishing our own bookkeeping as the park's statement. It is seeded from the
rides that have ever reported a `RETURN_TIME`, `BOARDING_GROUP` or
`VIRTUAL_QUEUE` row; the statement and the four things in it that are
load-bearing are in `docs/admin/curation.md`. The live badge built from the
queue types is untouched — one is the ride's layout, the other is today's
reading of it.

`PAID_RETURN_TIME` is left out of the seed although PAR-385 named it. It is a
return window, but it is the paid one — Genie+, Lightning Lane, Express — and
that product already has `has_fast_pass`, `fast_pass_name` and
`fast_pass_price`. Counting it would quietly widen the column from "you join
this instead of queueing" to "has a return window of some kind". Measured
against production, it adds 36 rides to the 140 — all of them Disney, none at
Universal, and they are `"it's a small world"`, `Pirates of the Caribbean`,
`Big Thunder Mountain` and their like: ordinary standby queues that also sell a
return window. The question is written down beside the statement rather than
decided here.

The seed has not been run. It needs the production database, which the cloud
runner has no access to — and it needs this change deployed first, because the
column it writes to does not exist until `synchronize` adds it. Counted from the
production host on 2026-09-22, it will move **140** attractions, Danse Macabre
among them. `VIRTUAL_QUEUE` contributes none of them: it matches zero rows in
the whole history, which is the same finding as the dead branch seen from the
data side.

The descriptor in `curated-field.spec-list.ts` is the whole of the admin change.
The editor generates itself from what the API describes, so the column appears
there with no frontend commit.

`VIRTUAL_QUEUE` was the other half, and the fix is prophylactic — worth saying
plainly, because the enum member reads like a feature that broke. No source we
ingest can currently produce the key: ThemeParks.wiki's live payload does not
publish it, and the Wartezeiten source maps its own `virtualqueue` status onto a
`RETURN_TIME` entry (`wartezeiten-data-source.ts:129`). Production agrees — not
one `queue_data` row has ever carried the value. What was true is that
nothing could have handled it if one arrived. The `QueueData` payload type had
no key for it, so the value was unreachable by construction and the ingestion
switch had no branch; a row would have carried a status and nothing else — no
state, no return window. The delta strategy had the same gap one function down,
so a row that somehow held a window would not have been written again when the
window moved. Both now map against `RETURN_TIME`'s branch, which carries the
same three fields, and both have a spec that goes red without them.

The three hand-written lists of queue types now read the enum instead of
repeating it. The one in `parks.controller.ts` had drifted furthest: it named
three of the seven members, offered `PAID_FASTPASS`, which has never been one,
and omitted four — `PAID_RETURN_TIME`, `BOARDING_GROUP`, `PAID_STANDBY` and
`VIRTUAL_QUEUE`.

Only one of the three rejects anything, and it is worth being exact about which:
`attraction-query.dto.ts` validates with `@IsIn(Object.values(QueueType))`. The
other two are `@ApiProperty` / `@ApiQuery` declarations — they document the type
and do not check it. `parks.controller.ts` in particular takes
`@Query("queueType") queueType?: QueueType` with no pipe, so an unknown value
still reaches the enum column and comes back as a 500 rather than a 400
(measured against the running API, PAR-401). That gap predates this change and
is not closed by it; what closed is the drift between the lists and the enum. Three prose lists that count the types rather than validate
against them are corrected alongside — `queue-data.module.ts`,
`queue-data.entity.ts` and `queue-data.service.ts`, all three of which said six.
