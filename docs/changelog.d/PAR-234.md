### Fixed — the E2E schema reads its hypertables from the service that creates them

Production runs seven hypertables and the park merge writes to every one of
them. `test/global-setup.ts` converted three, so `weather_data`,
`wait_time_predictions`, `forecast_data` and `queue_data_aggregates` were plain
tables in the suite that is supposed to answer what a merge does to a
compressed chunk. That answer came back green: the tables existed, so the
schema guard's `to_regclass` check passed, and
`TimescaleInitService.enableCompression` is a silent no-op on a
non-hypertable.

The list had drifted twice — one entry until PAR-172, three until now — because
it was a second copy of a list that already existed. The seven now live in
`src/database/hypertables.ts` as data, carrying the table, the partitioning
column, the `chunk_time_interval` and the compression settings
`TimescaleInitService` passed per call. The service iterates that list, so
production's schema is built from exactly the same arguments as before; the E2E
schema imports it. Adding a hypertable is one line in one file, and it reaches
the test schema and the assertion without anyone remembering to copy it — the
same rule `test/helpers/ml-forecast-tables.ts` follows for the DDL of the
tables no entity owns, minus the text scan, because this writer is importable
TypeScript.

Measured against production on 2026-09-17: all seven intervals in the new
constant are the ones `timescaledb_information.dimensions` reports (1 day for
`queue_data`, `show_live_data`, `restaurant_live_data` and `forecast_data`,
7 days for `weather_data`, `queue_data_aggregates` and
`wait_time_predictions`), and `wait_time_predictions` is still the only table
with a `compress_segmentby`.

`park-merge.e2e-spec.ts` now checks name, partitioning column and chunk
interval per table against that constant instead of three names, and a new case
covers the `weather_data` step: two parks holding a row on the same date come
out as one row per date, the loser's duplicate discarded and its other row
moved across a chunk boundary. Forgetting that table raises nothing — the
foreign key is `ON DELETE CASCADE`, so the park delete would have taken the
weather history with it inside a transaction that reports success.
