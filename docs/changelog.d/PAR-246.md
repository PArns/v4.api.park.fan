### Fixed — the nightly schedule cleanup keeps one row per park, day **and ride** instead of one per park and day

`schedule_entries` holds the park's opening hours (`attractionId IS NULL`) and
per-ride rows in the same table. `cleanupDuplicateScheduleEntries` and its
per-park twin partitioned phase 1 on `("parkId", date, "scheduleType")` and
phase 2 on `("parkId", date)` alone, so each pass kept **one row per park and
day** — the opening hours or a single ride, decided by whichever carried the
newer `updatedAt`. PAR-171 fixed the same blind key on the merge path; this is
the gap-fill, and it runs unconditionally from `fillScheduleGaps` and
`fillAllParksGaps` rather than from an admin action.

Measured against a real PostgreSQL 16 on one park-day holding the park's
OPERATING row, a gap-filled UNKNOWN placeholder, two rows for ride A and two
types for ride B (8 rows over two parks):

| | rows kept | what survives for park 1 |
| -- | -- | -- |
| before | 2 | ride A's OPERATING row — **the park's opening hours are deleted** |
| after | 4 | the park's OPERATING row, ride A's, ride B's |

That deletion is the interaction the PAR-171 entry below names: a per-ride row
reparented by a merge carries its old `updatedAt`, so it can outrank the
winner's own park-wide row and take it out on the next nightly pass. Both halves
are closed now.

Phase 2's pre-filter is an `EXISTS` with `IS NOT DISTINCT FROM` rather than the
row-wise `("parkId", date) IN (SELECT …)` it replaced: adding the nullable ride
to that form evaluates to NULL for every park-level row, which would have
excluded exactly the rows the priority rule is written for. Same operator and
same reason as `migrateScheduleEntries`. The statements now live in
`src/parks/utils/schedule-dedup.sql.ts`, built once for the global and the
per-park scope, so the rule has one derivation per path and not three. A second
global sweep over a settled table deletes 0 rows.

**Two read paths in the same two methods had the same blindness**, neither of
them a delete, which is why the ticket did not see them.
`saveScheduleData` looked its existing row up by `(parkId, date)` and keyed the
map on `date|scheduleType`, so a per-ride row of that day and type answered for
the park and was handed the park's opening times while staying attached to its
ride. `fillScheduleGaps` read its window by `(parkId, date-range)` and keyed the
map on the date alone, so a per-ride row occupied the day: the park never got
its own gap-filled row for it, and the UNKNOWN→CLOSED promotion and the
gap-filled-CLOSED→UNKNOWN demotion — both decided by the **park's** operating
range — rewrote the ride's row instead.

`fillScheduleGaps` splits the two uses of that set rather than filtering it. The
row it may **rewrite** is park-level, as above; the days it may **insert** on
count every row, per-ride included. Filtering both would have written a
"Gap-filled" CLOSED onto exactly the park-days the old cleanup damaged — the
`ride A's OPERATING row survives, the park's does not` case measured above —
and that is a confident claim built from an absence (claude.md §4). It is also
not symmetric: inside the park's season a gap-filled CLOSED cannot be demoted
again, and the analytics joins read CLOSED as "drop this day's queue data from
P50/P90" (`analytics.service.ts`, the
`se.id IS NULL OR se."scheduleType" IN ('OPERATING','UNKNOWN')` filter) while
they read a missing row as "keep it". Reconstructing the lost rows is out of
scope; writing a wrong one in their place is not the alternative.

Both of those keys are built by one helper now, and it stopped converting: a
PostgreSQL DATE arrives from TypeORM as a `"YYYY-MM-DD"` string, which already
names the day. Reading it as `new Date(str)` yields UTC midnight, and formatting
that in a park west of Greenwich answers with the **previous** day — every park
in the Americas, on every row, so `fillScheduleGaps` filed each row one day
early, saw the real day as a gap, and aimed its promotion and demotion at the
neighbour. That expression predates this change and is unaltered elsewhere; it
is corrected here because the new second reader rests on the key being the row's
own day. `AttractionIntegrationService` has carried the same guard, with the
same reasoning, for as long as it has had a schedule map.

`saveScheduleData` now filters `attractionId IS NULL`,
as `hasOperatingSchedule`, `getBatchHasOperatingSchedule`, `isParkSeasonal` and
`getOperatingDateRange` already did; there is a partial index for it
(`idx_schedule_park_date_no_attraction`). The three placeholder DELETEs in
`saveScheduleData` carry the same filter.

**And seven readers were relying on the bug.** `getSchedule`,
`getScheduleForDate`, `getNextSchedule`, both halves of `getBatchSchedules`,
`isParkCurrentlyOpen` and `isParkOperatingToday` all answer a question about the
park and none of them filtered on the ride; the two `findOne` calls have no
`ORDER BY` either, so they take whichever row the plan hands back first. They
were correct only because the cleanup collapsed each park-day to one row before
they ever read it. Keeping a per-ride row is exactly what this change does, so
all seven now say `attractionId IS NULL`. `isParkOperatingToday` is the one that
mattered most: `WaitTimesProcessor` asks it whether to fetch live data at all.

**Nine more sat outside `ParksService`**, and they are part of the same blast
radius rather than a follow-up: `getEffectiveStartTime`, `getEffectiveEndTime`,
`getBatchEffectiveStartTime` and the per-day P50 window in `AnalyticsService`
(the first three order by `openingTime ASC`, so a ride that opens before its
park would have won); the ML feature path's "park opening time today", its
`parkHasSchedule` data-quality flag and its batched schedule lookup; the search
index's `getBatchParkHours`, whose loop is last-write-wins per park; and the
cache warmup's "parks opening in 12 h", where the cost is only a warmed cache
nobody needed. A reader of the park's hours that can be answered with a ride's
row is wrong whether or not the set is empty today, and each of these is one
line.

How many per-ride rows production holds is still not measured — the same open
question `merge-dependencies.ts` records for the merge path. The fix is right
under either answer: on an empty set every statement here is a no-op.
