### Changed — the park payload carries `typicalWaits` for every ride with 20 measured days, not only headliners

The nightly typical-waits job stored the P50/P90 peak-wait stats only for tier1/tier2
headliners, so the park payload — the one the SSR ride page renders from — carried them for
10 of Europa-Park's 97 attractions, while 84 have the 20 operating days the detail endpoint
already treats as displayable. The job now stores every ride that clears that floor.

The payload is the full detail-endpoint `TypicalWaitsDto`, `byDayOfWeek` included: the
frontend's `AttractionTypicalWaits` maps over it unguarded, so a slim projection would
throw on every ride page. Measured cost on Europa-Park, rebuilt from production rows:
149.5 → 208.2 KB uncompressed (+58.7 KB), 16.7 → 17.8 KB brotli (+1.05 KB). The 5-minute live poll (`LiveParkSnapshot`) already leaves `typicalWaits` out.

The job got cheaper while covering more: one grouped scan of `queue_data_aggregates` per
park (`(parkId, hour)` index) instead of one query per ride — ~0.25 s against ~5.9 s for
Europa-Park, where each per-ride query paid ~60 ms of planning over the year's chunks. Both
paths build the payload with the same `buildTypicalWaits`, and the job primes the detail
endpoint's cache, so the two serve identical numbers for the day.
