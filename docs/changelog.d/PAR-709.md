### Changed — the E2E database is pinned to the version production runs

`test/global-setup.ts` started the suite's database as
`timescale/timescaledb:latest-pg16`. Production runs PostgreSQL 18.6 with
TimescaleDB 2.24.0, so both axes were off and in opposite directions: PostgreSQL
a major version behind in the test, TimescaleDB six minor versions ahead
(16.15 / 2.30.2). The container now starts `timescale/timescaledb:2.24.0-pg18`,
which reports 18.1 / 2.24.0.

PAR-704 hit it from both sides. `UPDATE … SET id = …` on a primary-key column of
a compressed chunk is refused from TimescaleDB 2.30 on and goes through on
2.24.0 — so the test would have failed a write the running server accepts, and
behaviour that only holds up to 2.24 was invisible in the suite that exists to
measure what a merge does to a compressed chunk.

The pin rather than `latest-pg18` is the point. The production container's image
tag *is* `latest-pg18` and it runs 2.24.0, while that tag serves 2.30.2 on the
registry today: a running instance is the state of its last pull, so the tag
names no version. Matching the tag would not have matched the version. The two
compose files keep `latest-pg18` — pinning those changes what the next deploy
runs, which is a deploy decision.

PostgreSQL is now matched at the major version rather than exactly, 18.1 against
18.6, and that is deliberate: the image couples the two versions, so a base of
18.6 only comes with TimescaleDB 2.30.x. Taking the TimescaleDB match and a
five-patch PostgreSQL gap keeps the axis the measured differences were actually
on. Where the pin comes from and how to move it when production's version
changes is in
[docs/development/e2e-database-version.md](../development/e2e-database-version.md).
