### Fixed — CatBoost training registers its own metrics, fails honestly and stays inside its timeout

Faults in the daily CatBoost training and serving path:

- **Old metrics under a new version.** The training processor read the new
  model's metrics from `/model/info`, which describes whatever model the
  answering worker has loaded. A worker only reloads on its next `/predict`, so
  after a 60 s wait the processor took the previous model's metrics and stored
  them under the new version. The champion/challenger gate then compared the
  champion with itself: `v20261006_0600` was stored with MAE 5.06, the value of
  `v20261003_0600`, while its own metadata file said 4.433 (also
  `v20260929`/`v20261001` and `v20260905`/`v20260906`). The ml-service now
  serves `GET /model/info/:version` from that version's own `.cbm` + `.pkl`, the
  processor registers from it, and a version with no saved metrics is not
  registered at all.
- **Activation order.** The training subprocess used to write the
  active-version sentinel itself, before the API had registered the version or
  run the gate, so a rejected or failed run had to be reverted afterwards — a
  revert that raced threadpool reloads and could flip the workers back. Training
  now only writes the model file, its metadata and the status; the processor
  activates (`POST /model/reload`, which loads the DB-active row and writes the
  sentinel) only after the `ml_models` row is saved and the gate passed. If the
  reload does not confirm the new version, the DB is rolled back to the
  previous champion. A rejected, failed or timed-out run never touches what is
  served.
- **Phantom versions.** `train_standalone.py` reported `completed` and wrote
  the sentinel even when `train_model` returned early (no data, empty training
  set) and saved nothing. Workers then retried loading a missing file on every
  request. An early return is now a failure.
- **Training time ran into the timeout.** History starts 2025-12-24 and the
  window only closes at `TRAIN_LOOKBACK_YEARS` (2), so the pool grows every
  day: 1682 s on 2026-09-04, 2520 s on 2026-10-07 against a 2700 s limit.
  `ML_TRAINING_TIMEOUT_MINUTES` now defaults to 90, and each run records the
  duration and row counts of fetch, feature engineering and fit
  (`training_timings` in the metadata, `timings` in `/train/status`), so the
  next run shows which phase grew. The model still trains on the full pool. An
  opt-in `TRAIN_MAX_ROWS` (default 0, off) can thin rows older than
  the newest `TRAIN_FULL_RESOLUTION_DAYS` of the pool (days 30–120 before the
  newest data, since the 30-day hold-out is split off first) by a uniform
  sample. It is not enabled and should
  only be switched on after an A/B (full vs capped) on an out-of-time window.
- **The served model never learned the newest 30 days.** `train.py` split off
  a 30-day chronological hold-out, only scored on it and never folded it back,
  so a season change (the start of Halloween) reached the model a month late.
  The early-stopped fit is now scored on the hold-out, its `holdout_metrics`
  (MAE overall and on busy rows ≥ 60 min, sample counts) are saved in the
  metadata, and the served model is refitted on all rows with the early-stopped
  tree count, the same dropout and the same sample weights.
  `TRAIN_REFIT_ON_ALL_ROWS` (default on) can switch it off; the gate still
  reads the validation MAE.
- **Model files were never deleted.** `cleanupOldModels` called `fs.unlink` on
  `/app/models`, which the API container does not mount, so neither retired
  versions nor versions that never got an `ml_models` row (failed, timed-out or
  unregistered runs, ~60 MB each) were removed — `/app/models` had grown to
  3.5 GB. The ml-service now lists and deletes a version's `.cbm`/`.pkl`
  (`GET /models/files`, `DELETE /models/files/:version`; safe version names
  only, and never the sentinel, loaded or in-training version), and the
  cleanup also removes orphans older than two days.
- **HTTP 500 "dictionary changed size during iteration".** The recent-history
  caches in `predict.py` were iterated while another threadpool thread of the
  same worker inserted. Eviction now runs over a snapshot under a lock.
