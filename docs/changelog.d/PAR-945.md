### Security — admin logins and curation writes hold up under parallel requests

The account lockout counted from the row read at the start of the request, so a
hundred parallel wrong passwords all wrote `failed_login_count = 1` and the
account never locked; it is now one atomic `UPDATE … RETURNING`. The Redis login
limiter counts each attempt before the ~100 ms password check and hands back the
ones that were not failures, instead of counting after it. A TOTP step is
claimed with a conditional `UPDATE`, so a code replayed in parallel is accepted
once. A login re-reads `is_active` and `role` after creating its session, so a
deactivation or demotion that landed mid-login is not outlived.

Curation (`curateAttraction`, `curatePark`, the bulk ride edit) and account
updates write only the changed columns instead of `save()`-ing the whole stale
row, which let concurrent edits of different fields revert each other. The bulk
ride edit and `retire` validate every entry before writing any (an invalid
`retiredAt` is a 400), and publish whatever was written even if a later write
fails.
