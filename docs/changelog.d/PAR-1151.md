### Added — park.fan's own cookieless statistic: page views, visits, events and SEO reports

New module `src/site-analytics/`. `POST /v1/analytics/collect` takes a batch of up to 20 page views
and events from the browser's beacon (`text/plain` from `sendBeacon` or JSON), checks every hit
against a pattern, and answers 204 whether it counted or not. The server adds browser and OS
family, the country from the GeoLite2 lookup, and per visit the referrer site and its channel
(`search`, `ai`, `social`, `referral`, `campaign`, `direct`). Bots, `DNT: 1`, `Sec-GPC: 1` and, in
production, any origin other than park.fan are not counted; no address or User-Agent is stored or
logged, and every Redis key that stands for a reader is an HMAC under `ANALYTICS_HASH_SECRET` (new,
optional, falling back to `PAGE_VIEWS_HASH_SECRET`). Events need no schema: generic daily guards
cap hits per address (3000), event names (300), page types (100) and property combinations per
event (2000, past it `_overflow`), and the admin can block a name.

Counts go into five-minute Redis buffers without TTL; the `site-analytics` queue's `flush` writes
each finished window once into the insert-only hypertables `site_pageviews` and `site_events`
(one row per combination of all dimensions, compressed after seven days, chunks dropped after 400
days by `drop-old-chunks`), so nothing is ever updated or deleted. Visits, bounce and realtime come
from Redis; `snapshot-visitors` keeps each day's visitors in `site_visitor_days`. A merged park,
ride, show or restaurant is recorded in `site_entity_merges` and resolved when the reports read.
Ten admin reports under `/v1/admin/analytics/` (overview, breakdown, events, one event, crosstab,
search, SEO landing pages, trends, not found, uncovered) take `days`, `locale` and Umami-style
`filter=<dim>:<value>`; the block list is `PUT`/`DELETE /v1/admin/analytics/blocked-events/:name`.
Measured on a synthetic year at ten times today's traffic: 430 MB on disk, 22 ms to flush a window,
0 dead tuples, 30-day reports under half a second. See
[site statistic](frontend/site-analytics.md).

### Changed — the most-read rankings run on the site statistic

A counted read is now the event `page_read`, with the same kinds, keys and caps (three per reader
and page, 500 per address and UTC day). `GET /v1/page-views/top` and `GET /v1/admin/page-views`
keep their answers and read `site_events`; `page_view_days` is no longer written, and its rows are
copied into `site_events` once at the first start (marker in `site_analytics_imports`). The table
stays until a later release drops it. See [page views](frontend/page-views.md).

### Deprecated — `POST /v1/page-views`

Records the same `page_read` and stays for one release, so pages cached with the old beacon keep
counting; the frontend sends `page_read` to `/v1/analytics/collect`.
