### Added — park.fan's own cookieless statistic: page views, visits, events and SEO reports

New module `src/site-analytics/`. `POST /v1/analytics/collect` takes a batch of up to 20 page views
and events from the browser's beacon (`text/plain` from `sendBeacon` or JSON, 16 KiB at most),
checks every hit against a pattern, and answers 204 whether it counted or not, with
`Cross-Origin-Resource-Policy: cross-origin` so the browser does not block the beacon's answer. The
server adds browser and OS family, the country from the GeoLite2 lookup, and per visit the referrer
site and its channel (`search`, `ai`, `social`, `referral`, `campaign`, `direct`; only a search
engine's own host is `search`). Bots, `DNT: 1`, `Sec-GPC: 1` and, in production, any origin other
than park.fan are not counted; no address or User-Agent is stored or logged, and every Redis key that
stands for a reader is an HMAC under the UTC day's key, derived from `ANALYTICS_HASH_SECRET` (new,
optional, falling back to `PAGE_VIEWS_HASH_SECRET`), so it is a pseudonym for one day; none lives
longer than about 25 hours. `nearby_parks_loaded` and the `compass_*` events keep no entity.

Events need no schema. Generic daily guards, each an atomic Redis script, cap hits per address
(3000; IPv6 counted per /56) and per five-minute window (5000), and the distinct event names, page
types, paths, referring sites, campaigns and property combinations a day may bring, with a small
budget of new values per address and yesterday's values always admitted, so nobody can fill a guard
after midnight and lock out the site's own events. Past a guard a hit is dropped or stored under
`(other)`, `other` or `_overflow`, and counted by reason; blocking a name frees its place.

Counts go into five-minute Redis buffers without TTL, in one `MULTI` per request; with Redis away an
instance holds at most 5000 fields in memory and writes them once a minute. The `site-analytics`
queue's `flush` writes each finished window once, under a claim, into the insert-only hypertables
`site_pageviews` and `site_events`, bucketed by the UTC hour (compressed after seven days, chunks
dropped after 400 days by `drop-old-chunks`), window by window so one that fails does not hold up
the rest. A page view's row and an event's row carry no visit dimension; only the row that records a
visit start and its `engaged` carries the entry, referrer, channel and campaign. Visits, bounce and
realtime come from Redis; `snapshot-visitors` keeps each day's visitors in `site_visitor_days`. The
system-health report shows the flush backlog and the day's drops. A merged park, ride, show or
restaurant is recorded in `site_entity_merges` and resolved when the reports read.

Ten admin reports under `/v1/admin/analytics/` (overview, breakdown, events, one event, crosstab,
search, SEO landing pages, trends, not found, uncovered) take `days`, `locale` and Umami-style
`filter=<dim>:<value>`; a filter on a visit dimension selects visits, and the reports that count page
views or events refuse it. The window before ends at the current hour and is null past 180 days. The
block list is `PUT`/`DELETE /v1/admin/analytics/blocked-events/:name`. Measured on synthetic data at
ten times today's traffic: about 410 MB for a year, 19 ms to flush a window, 0 dead tuples, 30-day
reports under 300 ms. See [site statistic](frontend/site-analytics.md).

### Changed — the most-read rankings run on the site statistic

A counted read is now the event `page_read`: three per reader and page, ten per address and page and
200 per address and UTC day (was 500), and only of a park or ride that exists. `GET
/v1/page-views/top` and `GET /v1/admin/page-views` keep their answers and read `site_events`; the
public ranking lists a park or ride only while it exists. `page_view_days` is no longer written, and
its rows are copied into `site_events` once at the first start (marker in `site_analytics_imports`).
The table stays until a later release drops it. See [page views](frontend/page-views.md).

### Deprecated — `POST /v1/page-views`

Records the same `page_read`, with the same origin check as the collect endpoint, and stays for one
release, so pages cached with the old beacon keep counting; the frontend sends `page_read` to
`/v1/analytics/collect`.
