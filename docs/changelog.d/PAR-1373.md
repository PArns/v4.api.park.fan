### Added — visitor accounts with synced favorites, ridden rides and temperature unit

A new role `user`, below `developer`, is a visitor's own account on park.fan. `POST
/v1/account/register` creates it and signs it in; `GET /v1/account` and `PUT /v1/account/data`
read and write its favorites, ridden rides and temperature unit (table `account_data`); `DELETE
/v1/account` deletes it with its password. It reaches nothing of the developer API, the admin or
MCP. Developer and visitor registration share one flow (`SelfRegistrationService`), and developers
can now delete their own account too.

Each account also has its own storage for members-only features: `GET /v1/account/storage` lists
the keys, `GET`, `PUT` and `DELETE /v1/account/storage/:key` read, write and remove one JSON value
(at most 64 KB, 100 keys per account). It is erased with the account.

From a review of the key and account code:

- Approving, rejecting, reopening and withdrawing a request is one conditional UPDATE, so two
  approvals at once issue one key, not two.
- Deleting an account deletes the account first, under the last-owner lock, and only then its
  sessions, keys, requests and stored data, so a refused deletion leaves everything in place.
- Every `:id` route checks the id with `CanonicalUuidPipe` (400 instead of a 500 from Postgres).
- `PUT /v1/account/data` writes only the fields it names, in one statement, and
  `temperatureUnit: null` clears the unit; a storage write is one statement too.
- Two registrations of one address at once answer 409 `account-exists` instead of 500.
- The account names behind keys and requests come from one query helper (`accountsByIds`), the key
  list reads its counters, park names and owners in parallel, and a developer's keys are deleted in
  one statement. The login answer, the session's principal, the minimum password length, the
  self-service roles and the keyless permission set are each defined once.
