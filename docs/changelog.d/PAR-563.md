### Added — ad-hoc SQL against production now runs under a deadline

On 2026-09-28 a research `SELECT` started through `docker exec … psql` stayed open
after the runner process that launched it had exited. The TimescaleDB compression
policy on `queue_data` then asked for a strong lock, queued behind that snapshot,
and every reader queued behind the policy: 90 queries piled up, the TypeORM pool
ran into its 15-second acquire timeout, and the whole public API — `/v1/health`
included — answered HTTP 500 for about 32 minutes. Nothing about the query was
wrong except that it had no deadline: `statement_timeout`,
`idle_in_transaction_session_timeout` and `lock_timeout` are all `0` on this
server.

`scripts/prod-psql.sh` is now the way in. It resolves the postgres container,
whose name carries a Coolify deploy id, and sets `statement_timeout=5min`,
`idle_in_transaction_session_timeout=1min` and `lock_timeout=10s` on that session
through `PGOPTIONS`. Each is overridable per invocation for the rare query that
legitimately needs longer. Five minutes is generous rather than tight: of the 4962
statements `pg_stat_statements` recorded over the 117 days since its last reset,
six ever exceeded one minute and two ever exceeded five, and both of those are
background jobs rather than queries anybody runs by hand.

The limits stay on the session and are deliberately not set with `ALTER ROLE` or
`ALTER DATABASE`. The application pool connects as the same `parkfan` role as an
ad-hoc session — 103 pool connections against one `psql` when this was measured —
and so does the TimescaleDB background worker, so a role-level setting would cap
application queries and maintenance jobs as well. The pool already has its own
bound in `connectionTimeoutMillis`; whether it should also carry a query-runtime
limit is a separate question.

`idle_in_transaction_session_timeout` covers a gap `statement_timeout` cannot: the
latter never fires while no statement is running, so a session parked between
`BEGIN` and `COMMIT` would hold its snapshot and its locks indefinitely. Both were
verified against production — a statement cancelled after its limit, a parked
transaction terminated — while `/v1/health` kept answering 200 and a session
opened without the wrapper still reported `0`.
