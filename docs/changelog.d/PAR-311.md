### Fixed — a merge no longer strands the upstream id of the ride it deletes, and a stranded id no longer silences the ride that holds it

`external_entity_mapping` has no foreign key on `internal_entity_id`: the column
is a `character varying` and `internal_entity_type` decides at read time which
of four tables it points into. A merge that deletes the row a mapping names
therefore leaves the mapping behind, and nothing raises.

Two of the three merge paths already move the table before their DELETE, and
both say in a comment why it cannot live in `ATTRACTION_DEPENDENCIES` — it is
keyed across every entity type at once, so each caller moves it itself
(`ParksService.consolidateMergedEntities`,
`ParkMergeService.consolidateEntityData`). **`AttractionMergeService.mergeAttractions`
did not**, which is the path behind `POST /v1/admin/merge-attractions` and its
batch runner. It moves them now, before the dependencies and before the DELETE,
with no conflict delete for the same reason the other two give: the unique index
is on `(external_source, external_entity_id)` across the whole table, so a pair
the winner holds cannot also sit on the loser.

**What a stranded row costs is not tidiness.** That unique index means the dead
row keeps holding the upstream's id. `ChildrenMetadataProcessor.createMapping`
read the index as "a mapping exists", created nothing and said nothing — so the
live ride was left with no Queue-Times mapping, and `WaitTimesProcessor` cannot
resolve one without it: its `externalId` fallback covers `themeparks-wiki` only.
The ride then falls out of `seenAttractionIds` and
`reconcileMissingAttractions` writes it a permanent `system-reconciliation`
CLOSED series while the feed reports it open.

`createMapping` now separates the two cases the old `if (!existing)` collapsed.
A row naming an entity that still exists is a genuine conflict between two live
entities, `ParkMetadataProcessor` owns it and this path leaves it alone. A row
naming an entity that is gone is reclaimed, with a warning that names the dead
id. The existence check compares `id::text`, not a uuid cast: the column holds
text and a value that is not a uuid would raise 22P02 inside the sync.

`syncQtAttraction` wrote the mapping on the branch that creates a row and
nowhere else, so a ride that lost its mapping *after* it was created never got
one back. It now calls `createMapping` on both branches; the call is a no-op
when the mapping is already correct, so it costs one indexed lookup per ride per
sync.

**Measured against production on 2026-09-18.** 201 stranded rows of 14,365
(1.4 %) — 108 `queue-times`, 66 `themeparks-wiki`, 25 `wartezeiten-app` on the
attraction side, two on the park side. **38 of them sit on the id of a live
entity**, and not one of those 38 entities has a mapping of its own for that
source. 30 are rides of one park (Energylandia, `qt-park-317`). Crossed against
that park's live feed the same minute, the separation is total and has no
exception:

```
 own mapping | stranded mapping | rides | silent | fed by queue-times
-------------+------------------+-------+--------+--------------------
 f           | t                |    30 |     30 |                  0
 t           | f                |     5 |      0 |                  5
```

All 30 were `is_open: true` upstream at that moment — Abyssus at 184 minutes,
Grotto Expedition at 181, Tidal Wave Twister at 179 — and CLOSED in our API.

The 201 rows are **not** deleted. Two of them show why that would have been the
wrong instrument: the two the ticket named from the 2026-09-17 Rockford merge
point at live rides again today, re-homed by `EntityMappingsProcessor`, which
upserts on `(externalSource, externalEntityId)`. The stock heals where a writer
reaches it, and with these three changes every writer does. A bulk DELETE would
have freed the ids without giving the 38 rides a mapping, because the branch
that writes one never ran for a ride that already exists — it would have removed
the evidence and left the symptom.
