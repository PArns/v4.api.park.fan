### Fixed — the attraction merge rehearsal names the curated works period it would delete

A survivor that already holds part of a works period keeps its own, so the
losing row's window is refused — and the losing row is deleted a moment later.
Neither half of the merge said so: the window is not in `inheritedColumns`
because it was not inherited, and it was not in `droppedCurations` either,
because that list is built from `ATTRACTION_DEPENDENCIES` and a curated column
on the attraction row sits in no dependent table. The "Probelauf" button
reported a slug and a handful of columns and stayed silent about the one
hand-written value the merge destroys.

`previewMerge` now lists it as a `droppedCurations` entry on the `attractions`
table, carrying the losing row's values under the names the curation editor
takes them back under, and `mergeAttractions` writes a warning with the same
values while the row still exists. Both read one function, so the rehearsal
cannot drift from the merge. All three routes to the loss are covered: the
survivor holding part of the set, a window refused as inverted, and an estimate
flag dropped from a window that otherwise travels.
