### Fixed — a host reboot no longer kills the API 10 s into an ordered shutdown

The 20 s shutdown deadline from PAR-903 was sized against Coolify's
`docker stop --timeout=30`, and that 30 s is Coolify's own number: it lives in
the command Coolify runs on a deploy, not on the container. Every other stop
path read the container's `StopTimeout`, which was unset, so Docker applied its
per-container default of 10 s and the deadline could not fire at all.

Measured on 2026-10-21, when an unattended NVIDIA driver update restarted
`docker.service` 75 s before the host rebooted: the API was signalled at
20:40:38.808 and dockerd logged `Container failed to exit within 10s of signal
15 - using the force` at 20:40:48.808. `logs/shutdown.2026-10-21.log` has the
`signal` line for that process and neither a `deadline-exceeded` nor an `exit`
line, because the SIGKILL arrived 10 s before the 20 s deadline would have —
31 Bull queues went down with their job locks held, which is the outcome
PAR-903 exists to prevent. `stop_grace_period: 30s` on the `api` service sets
the container's own timeout, which is the value those paths read.

That covers a reboot as well. dockerd's `--shutdown-timeout` (15 s when unset)
is only a floor: moby's `Daemon.ShutdownTimeout()` raises it to the largest
container `StopTimeout` plus 5 s and then stops each container with its own
timeout, so a daemon shutdown now waits 35 s — inside systemd's 90 s for
`docker.service` — and the 20 s deadline can fire on every stop path. Changing
`/etc/docker/daemon.json` (PAR-1055) is therefore not needed for this. After a
deploy, `docker inspect -f '{{.Config.StopTimeout}}' <api container>` must
print 30, not `<nil>`, to confirm Coolify passes `stop_grace_period` through.

The `Redis is already connecting/connected` rejections in the same shutdown are
Bull's, not ours, and they are documented rather than changed.
`whenCurrentJobsFinished()` (bull@4.16.5 `lib/queue.js:1383`) forces the
blocking client to reconnect so its pending BRPOPLPUSH aborts, and
`redisClientDisconnect()` resolves early while that client is still
`connecting` — so the `connect()` behind it meets a client that is already
connecting. It surfaces as an *unhandled* rejection only because Bull builds
that promise before it awaits `Promise.all(this.processing)` and chains the
handler on afterwards; reproduced against a throwaway Redis, the
`unhandledRejection` is followed by a `rejectionHandled`, while the same
shutdown with a connected blocking client stays silent. The PAR-903 crash
handler already logs it without ending the shutdown.
