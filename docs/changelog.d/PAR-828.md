### Added — Chronos-2 and TimesFM 3.0 as ml-bench plug-ins, scored like every other candidate

`ml-bench/mlbench/models/foundation.py` plugs the two time-series foundation models
into the PAR-827 benchmark through the restricted plug-in interface, so they are paired
against the same baselines on the same rows as everything else. Chronos-2 takes a whole
park as one multivariate task (every ride a variate, the covariates shared); TimesFM 3.0
caps variate attention at 32, so each ride is a univariate task. Both run on a
compressed context of operating-window slots only — nights and closed days left out,
the day boundary carried by the covariates — with the regular-grid layout and a
covariate-free variant as controls, plus an ORACLE-weather variant reported separately
as an upper bound. A daily level path feeds the harness's `level × H5` composition so
d10–d90 are scored without asking for 15-min slots there.

On the live surface Chronos-2 beats both servable profile incumbents at every lead from
15 to 120 minutes — against `h5` by −4.02…−2.05 min and against `lvlh5_tft` by
−3.75…−1.87 on all rides, up to −8.23 on ex-ante busy rides — and beats `persistence`
from 30 minutes out (−0.42…−2.27 all rides, −0.92…−4.51 busy), losing to it only at 15
minutes. On the 0–45 minute plan-block correction it halves the incumbents' error
(6.77 min against 12.89 for `h5`). In the planner it is narrower: the regular-grid
layout beats the compressed one at all eight leads, the covariates are worth
0.39–0.82 min, perfect weather foreknowledge is worth under 0.12 min — so weather is not
the missing ingredient — and every variant loses to `h5` at d2. The crowd calendar (UC4)
was **not measured**: the every-7th-origin subset leaves at most five forecast days per
park-month against a minimum of eight, so no park-month unit is built at any lead.
TimesFM-3 was **not scored** and is reported as a drop on stated technical grounds: its
quantile head is fixed at 0.1–0.9, so it has no q95, which BENCH-SPEC requires for UC3
and D8. Chronos-2 is Apache-2.0; the TimesFM 3.0 weights are non-commercial, which
covers this benchmark but leaves production serving as an owner decision.

The harness gained `--parks` for subset runs that still re-score the baselines on
exactly the same parks, `run --pair-with` / `report --vs` for paired
model-against-model intervals (they have to be requested at run time, because the
per-slot forecasts are not kept), a separate q95 denominator for models whose quantile
head stops at 0.9, and opt-in pre-origin covariates for context models. A run's git SHA
is now written into the image as a file as well as an environment variable, and the run
script refuses to start — and declares a finished run void — when the SHA cannot be tied
to a commit containing the harness fixes the scores depend on.

### Fixed — a long-context plug-in could not be scored, and intraday origins reused one context

`HistoryView` is materialised and capped at `BenchConfig.history_days` (56), raising
above the cap. The foundation plug-ins ask for 343 days of compressed context and 400
for the daily head, so every Chronos-2 origin raised `ValueError`. Raising is what made
that safe — a cap that truncated would have published numbers from a shortened context
with nothing in the output to show it — so a model now declares what it needs via
`Model.truth_history_days`, read off the class so an instance attribute cannot widen an
information budget, and `Runner.history_days_needed()` takes the max over the registered
models.

The history view was also cached on `(origin date, origin table name)`, but the intraday
path reuses the name `oh` for every origin hour, so 08:00's context was served at
10:00…20:00 and every later intraday origin forecast from a context frozen at the first
hour of the day. The key now includes the information cut itself.
`test_information_cut_plugins` asserted the intraday frames do *not* move when the
origin day's truth is poisoned, which held only while that staleness bug did; it now
runs one pass per cut.
