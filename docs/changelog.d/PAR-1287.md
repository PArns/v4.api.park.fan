### Added — forecasts need a data API key; the API states its terms

Every ML forecast now leaves the API only to park.fan's own frontend (the
throttle bypass key it already sends) or to the holder of a data key in
`X-API-Key`. `/calendar`, `/best-days`, `/predictions/yearly` and `/plan/day`
answer 401 without one (`api-key-required` or `api-key-invalid`, with the terms
URL). Park detail, ride detail, `/stats/day` and `/favorites` keep answering
without a key but leave their forecast fields out (`bestVisitTimes`,
`hourlyForecast`, `predictionAccuracy`, `forecast`, `predicted`,
`forecastError`) unless `?forecast=true` comes with a key. The flag is a second
URL rather than a reaction to the key because Cloudflare caches by URL and
ignores `X-API-Key`. A keyed answer is always `private`: `keepResponsePrivate`
wraps `setHeader`, so no interceptor or handler can make it public again, and
the guard applies it before deciding, since its 401 runs ahead of every
interceptor and used to leave with no `Cache-Control`.

Keys are issued by an owner through `/v1/admin/api-keys` (list, create,
revoke, audited) and stored as SHA-256 in `api_keys`; `ApiKeyService` caches
a lookup in Redis for five minutes (one for a refused key) and forgets it on
revoke. `GET /v1/api-keys/verify` checks a key without fetching a forecast.
The OpenAPI document carries the `api-key` scheme, `info.termsOfService` and
`info.license`; the README at api.park.fan/ marks the keyed routes and replaces
"UNLICENSED, contact the maintainer" with the terms: free for non-commercial
use with a credit, forecasts only with a key and commercially only under a
written agreement, the live data of the sources for non-commercial use only.
Contract: [data API keys](../frontend/api-keys.md). Frontend side:
PArns/park.fan#1201.
