### Added — forecasts need a data API key; the API states its terms

Every ML forecast now leaves the API only to park.fan's own frontend (the
throttle bypass key it already sends) or to the holder of a data key in
`X-API-Key`. `/calendar`, `/best-days`, `/predictions/yearly` and `/plan/day`
answer 401 without one (`api-key-required` or `api-key-invalid`, with the terms
URL). Park detail, ride detail, `/stats/day` and `/favorites` keep answering
without a key but leave their forecast fields out (`bestVisitTimes`,
`hourlyForecast`, `predictionAccuracy`, `forecast`, `predicted`,
`forecastError`) unless `?forecast=true` comes with a key. The flag is a second
URL rather than a reaction to the key because Cloudflare caches by URL and
ignores `X-API-Key`. A keyed answer is always `private`: `keepResponsePrivate`
wraps `setHeader`, so no interceptor or handler can make it public again, and
the guard applies it before deciding, since its 401 runs ahead of every
interceptor and used to leave with no `Cache-Control`.

Keys are issued by an owner through `/v1/admin/api-keys` (list, create,
revoke, audited) and stored as SHA-256 in `api_keys`; `ApiKeyService` caches
a lookup in Redis for five minutes (one for a refused key) and forgets it on
revoke. `GET /v1/api-keys/verify` checks a key without fetching a forecast.
The OpenAPI document carries the `api-key` scheme, `info.termsOfService` and
`info.license`; the README at api.park.fan/ marks the keyed routes and replaces
"UNLICENSED, contact the maintainer" with the terms: free for non-commercial
use with a credit, forecasts only with a key and commercially only under a
written agreement, the live data of the sources for non-commercial use only.
Contract: [data API keys](../frontend/api-keys.md). Frontend side:
PArns/park.fan#1201.

Each data key has an hourly allowance (`requests_per_hour`, default 1,000, null
for none), counted per key and clock hour in Redis; past it the answer is 429
with `Retry-After` to the next full hour, and every keyed answer reports
`X-API-Key-Hourly-Limit`, `-Remaining` and `-Reset`. The frontend's own key is
not counted. `PATCH /v1/admin/api-keys/:id` changes the allowance, and the list
carries `requestsThisHour`. With `FORECAST_SHARED_CACHE=vary` a keyed success
keeps its route's public cache policy and varies on `X-API-Key` and
`X-Auth-Key`, for a Cloudflare Cache Rule whose Vary setting names both with
`passthrough` (available on Pro; a header in the cache key is Enterprise only).
Unset, every keyed answer stays private.

The frontend gets a data key of its own (usage `internal`, no hourly
allowance), sent as `X-API-Key`; `FORECAST_BYPASS_KEY=off` then stops the
throttle bypass key from opening forecasts, so it only lifts rate limits.
`/plan/day` and `/stats/day` answer repeats from Redis (15 and 5 minutes,
`cachedJson`, a degraded day plan is not kept), because their keyed answers
are private and Cloudflare no longer absorbs them.

A key can be limited to some parks (`allowed_park_ids`, null for every park,
unknown ids refused with 400). The guard resolves the route's park through
`ParksService` and answers 403 `api-key-park-not-allowed` for another park,
before the hourly count; a route without a park (`/favorites`) answers such a
key 403 `api-key-park-required`. `/v1/api-keys/verify` reports the key's parks
and checks one given as `?park=continent/country/city/park`. `PATCH` and `POST`
on `/v1/admin/api-keys` take `allowedParkIds`; the list names the parks.

After a review: a revocation writes the refusal over the cached lookup and a
`PATCH` the new state, while lookups store only with `NX`, so a lookup in
flight can no longer keep a revoked key or an old park list alive for five
minutes. An `internal` key is never counted. `?park=` counts only on
`/v1/api-keys/verify`, which now checks exactly the presented key, never the
bypass key, and answers `allParks` rather than a null the API would strip. An
empty park list is a 400. Old park paths resolve through the rename aliases,
and the park and ride redirects keep the whole query, `forecast=true`
included. In vary mode a keyed answer is shared five minutes at most. The
hourly counter is one `MULTI`, and a Redis failure fails open.

Redis: `/calendar` and `/predictions/yearly` keep the answer as served (the
default calendar request, two part-months with the hourly curve, never filled
the month cache); `cachedJson` collapses concurrent misses and reads a corrupt
entry as a miss; `/stats/day` keeps "no curve" too and holds its answer two
minutes; a warm park payload is answered without loading the park's
relations; the yearly ML read no longer caches an outage for 13 hours, and a
partial one marks the answer degraded. The new keys live in `CacheKeys` under
`resp:v1` prefixes and are cleared with the park, with its calendar months
and by the admin flush; `best-days` now goes with the park too.

Public data reads without a data key are limited to 60 a minute and 1,000 an
hour per address (`THROTTLE_ANON_LIMIT`, `THROTTLE_ANON_HOURLY_LIMIT`), on top
of the circuit breaker; the routes park.fan's browser calls are exempt.
