### Fixed — a virtual line reaching FINISHED is stored when it happens, not up to an hour later

`isSignificantChange` compared status, wait time and the return window, but
never `state`. A virtual line that stops handing out slots keeps publishing the
same window, so none of those three moved and the transition waited for the
60-minute rule to write a row anyway. The same held the other way round in the
morning.

Measured against production over 30 days before the change: 894 such changes,
median delay 1:04:53 — 60 minutes plus one 5-minute poll, the signature of that
rule. They split into AVAILABLE → FINISHED (427), FINISHED → AVAILABLE (448) and
FINISHED → TEMP_FULL (19), spread over 456 ride-days.

The cost of comparing `state` is 29.8 extra rows a day against 196,299 written
into `queue_data`, so +0.015 %. The flutter case the measurement cannot see
directly — a state that moves and moves back between two stored rows — is
bounded rather than assumed: the producer polls every 5 minutes and the
60-minute rule samples each series hourly, so a state flapping at poll rate
would show up as roughly ten delayed changes per ride-day. The measured mode is
two, which is the daily cycle, once each way. The worst case that survives that
bound is 19,537 silent polls a day × the 3.751 % per-poll change rate seen in
densely observed windows = 733 rows a day, +0.37 %.

Nothing changes on rollout: all 159 active series already carry a `state` on
their newest row, and 30 days hold no row without one, so the comparison cannot
flap between null and set.
