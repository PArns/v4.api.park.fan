### Performance — redundant indexes dropped, health counts shared, no-op holiday rewrites skipped

Six indexes that duplicated another one are gone from the entities: the plain
`(attractionId, timestamp)` index on `queue_data` (297 MB over 293 chunks, a leading
prefix of `idx_queue_data_covering`), `idx_weather_1` on `weather_data` (the primary
key, column for column), and the non-unique `@Index()` twins of the `UNIQUE`
constraints on `destinations.slug`/`externalId`, `restaurants.externalId` and
`shows.externalId`. Production runs `synchronize`, which would drop them at boot with a
blocking `DROP INDEX` — on a hypertable one statement holding `ACCESS EXCLUSIVE` on
every chunk — so they are dropped by hand, chunk by chunk with
`DROP INDEX CONCURRENTLY`, **before** this deploy. The procedure, rehearsed on
TimescaleDB 2.24 / PG 18, is [DB Health Runbook §2a](../troubleshooting/db-health-runbook.md).

`/health` counted the last 24 h of `wait_time_predictions` (1.6 M rows, 106 ms) and of
`queue_data` on every build — 2 620 times a day each, about 280 s of database time.
Both counts now sit in Redis for ten minutes and serve every instance; a failed count
is never cached. The global `queue_data` row total is recounted every six hours
instead of hourly. `approximate_row_count('queue_data')` was measured as the cheap
alternative and rejected: it answered 1 346 100 431 against an exact 48 365 912.

The 03:00 lead-snapshot scoring wrote its rows through `save()`, one `UPDATE` each —
the 340-statement burst that queued for the pool at 03:00:02 on 2026-10-11. It is one
`UPDATE … FROM (VALUES …)` per 500 rows now, with the same values.

The holiday sync re-sends the same calendar every run and rewrote every stored row:
22 M updates on 200 k rows, 17 % dead tuples. The upsert now carries
`skipUpdateIfNoValuesChanged`, so an unchanged row is left alone; `updatedAt` moves
only when a holiday actually changed.

[DB Health Runbook §5a](../troubleshooting/db-health-runbook.md) is corrected: the
2026-10-12 06:15 OOM was 28 Node.js processes of the local Linear runner's 06:00 test
run (15.3 GB), not Postgres (0.51 GB). It also records what was changed on the host
and in Postgres that evening.
