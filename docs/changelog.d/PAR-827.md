### Added — ml-bench, one offline benchmark every model comparison runs through

`ml-bench/` is a new, undeployed Python package (own Dockerfile with PyTorch
cu128 for the RTX 5080, ruff, pytest) that implements the BENCH-SPEC of PAR-826:
a read-only export of production to Parquet (the STANDBY change log one UTC day
— one hypertable chunk — per query, 0.11–0.40 s each, through
`scripts/prod-psql.sh`), the 15-minute truth (value in force at the slot
midpoint, 3-hour staleness cap, inside the published window), a rolling-origin
backtest with a strict information cut (a test poisons everything after the
origin — truth, levels, both ends of a late-published window, every covariate —
and asserts no forecast moves on the daily, the daily-level and the intraday
path; opening hours are the ones whose schedule row was already written at the
origin, else a 56-day projection), baselines 1–6, a plug-in interface that hands
a model pre-fetched DataFrames and nothing else (no database connection is
reachable from any object it is given) and no weather unless it opts in, and a
report with park-day and park-cluster bootstrap CIs per use case (UC1–UC4), per
frontend decision (D1–D9: next-best ride, live correction, best time, planner
optimiser regret, rope drop, crowd bucket, day comparison and star, uncertainty,
coverage) and per lead — the horizon curve, the usable horizon and the hand-over
table the serving router will read. A model counts as better only where it beats
**every** naive candidate at that lead — the naive envelope, each comparison
paired on its own shared rows, with the park-cluster CI of the difference
excluding 0 over at least 10 distinct bootstrap units and a non-zero CI width.
The per-lead reference is BENCH-SPEC's naive ladder, moved off it only by a
significant PAIRED loss to another candidate, and every model is also scored
against each candidate individually (`cells_all_refs.csv`), so "nothing beats the
best naive" and "this model beats the weekday median" stay separable statements —
H5, for instance, beats the weekday median at every lead to d90 and the whole
envelope only to d5. LOW-N is applied per unit of analysis, so the crowd-calendar
use case is gated on park-months (~180 per lead) instead of on the three month
labels a 54-day window has, which is what used to make it untestable. Each report pass records the code that produced *it* (`report-<tables-dir>.json`), separately from the code that produced the run, because every verdict is recomputed at report time. Horizon curves are reported three ways — a fixed target window, the full period, and a fixed **origin** window (`--origin-from`/`--origin-to`) — because fixing the target days leaves the origin season drifting along the lead axis and fixing the origins leaves the target season drifting, so no single pass identifies the curve; where the three disagree the serving recommendation is the one they share. The truth still contains production's carried-forward
`is_heartbeat` rows; `build --drop-heartbeats` builds the alternative target and
both are published, with the sensitivity measured (2.2 % of the headline window's
slots, all of it in its autumn half, no serving band changed). See
docs/ml/ml-bench/results-baselines.md.
