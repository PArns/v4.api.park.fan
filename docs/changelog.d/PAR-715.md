### Fixed — live wait times are stored on the five-minute grid

On 2026-10-04 Movie Park's rides read 61 minutes where the park meant 60, in the site header and on the ride cards. On 2026-10-05 the wiki sent Europa-Park 1, 3 and 6, and `GET /v1/parks/europe/germany/rust/europa-park` served them unchanged in `attractions[].queues[].waitTime`.

`ConflictResolverService` rounds to five, but only the entity's `waitTime`. `WaitTimesProcessor.adaptEntityLiveData` passes the source's `queue` object on whenever there is one, which is every ThemeParks.wiki ride and every Wartezeiten ride with a wait, and `QueueDataService.buildQueueCandidates` wrote `queue.STANDBY.waitTime` as it came. The rounded figure never reached `queue_data`, and the park, attraction and favorites payloads read that column without rounding it again.

`buildQueueCandidates` now runs STANDBY, SINGLE_RIDER and PAID_STANDBY waits through `roundToNearest5Minutes` before the row is built. A posted `null` stays `null`. Exactly 13 minutes is the one value left alone: Disney posts it for a walk-on, so `roundToNearest5Minutes` now returns 13 unchanged (`WALK_ON_WAIT_MINUTES`) everywhere it is used, and `ConflictResolverService` rounds through the same function instead of its own `Math.round`, so a 13 survives the merge as well. Before this, the API's aggregates and the search and nearby endpoints turned a 13 into 15. A ride whose last stored row is off the grid gets a new row on the first poll after the deploy, because 60 against a stored 61 counts as a change. Readings of 1 and 2 minutes, which Europa-Park posts for walk-through rides and train stations, are now stored as 0, the figure the site already showed for them.

Not changed: with more than one source, the stored wait is still the queue object's figure, not the consensus `calculateConsensusWaitTime` works out. Covered by four cases in `queue-data.batch-write.spec.ts` and one in `wait-time.utils.spec.ts` (PAR-715).
