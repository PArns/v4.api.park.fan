### Fixed — a merge of two listed wiki ids no longer grows the loser back

A merge re-points the loser's `external_entity_mapping` rows onto the winner,
but nothing read them: `attractions.externalId` is one column, so when the wiki
keeps listing both ids of one ride, the loser's id matched no row on the next
children sync and was inserted again as a `-3` row — silently, because
`createMapping` then found the id already mapped. `syncAttraction` now looks a
listed id with no row up in `external_entity_mapping` before it inserts; if it
names an attraction of the same park, that row is stamped as listed and no
second row is created. The row keeps its own `externalId`. A mapping that names
a row of another park, or no mapping at all, inserts as before.

This changes nothing on its own (no merge of such a pair exists yet). It is the
precondition for merging the 8 same-ride pairs measured in PAR-949, all of
which have both ids listed.
