### Performance — the ML reads compare uuid to uuid, so Postgres can use the index

`qd."attractionId"::text = ANY(:ids)` cast the indexed uuid column to text,
which hid it from its index: TimescaleDB decompressed every `queue_data` chunk
in the window instead of filtering on the segment-by column. The two serving
reads in `ml-service/predict.py` (rolling stats and recent waits, ~90 000 calls
a day each) were ~80 % of all database time. Every such filter now casts the
parameter instead (`= ANY(CAST(:ids AS uuid[]))`, `= $1::uuid`):

- `ml-service`: `predict.py` (rolling stats, recent waits, `weather_data`,
  `schedule_entries`), `db.py` (historical occupancy, attraction ids of a
  park), `features.py` (`park_has_schedule`), `attraction_features.py`,
  `schedule_filter.py`.
- `pcn-service/db.py` and `nf-service/db.py`: attraction meta, the daily-peak
  panel and the weather read.
- NestJS: the TFT headliner read in `MLService.getTftDailyPredictions`, the
  stale-row sweep of `attraction_accuracy_stats` and the entity-existence probe
  in `ChildrenMetadataProcessor`.

A value that is not a uuid would make the cast fail the whole query, so ids are
filtered first (`uuid_params.py`, `isCanonicalUuid`), keeping only the form
`uuid::text` prints. Those are exactly the values the old text comparison could
match, so the rows are unchanged: identical on production for three parks and
five queries. Phantasialand, warm cache: rolling stats 264 781 → 28 195 buffers
and 289 → 93 ms, recent waits 198 643 → 50 520 buffers and 165 → 45 ms. The rule
is in `docs/ml/performance-optimizations.md` §5.
