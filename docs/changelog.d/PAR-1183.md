### Fixed — The weekly attraction-details sync resumes after a deploy instead of failing

`sync-attraction-details` walks ~7,000 rides at one request every 2 s, about
four hours. On 25 October two deploys landed in it: each restart began again
at the first ride, and Bull's default of one stall failed the job with "job
stalled more than allowable limit". It now walks the rides in id order and
stores the last one it finished as the job's progress, which Bull keeps when a
stalled job goes back to the queue, so the next container picks up after it;
`children-metadata` allows three stalls. See
[job queues](architecture/job-queues.md#a-job-a-deploy-stops).
