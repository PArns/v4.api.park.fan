### Documented — the schedule move, the schedule dedup and PAR-149's four tables now run against a real database

Until now the e2e suite seeded no `schedule_entries`, `ride_alerts`,
`prediction_lead_snapshots` or `attraction_review_marks` row, so the statements
for these tables were only checked as SQL text.

- **Park merge, both paths** (`repairDuplicates`, `mergeParks`): PAR-171's day
  in `test/e2e/park-merge.e2e-spec.ts` (opening hours on both parks, a ride on
  both, a ride only the loser has) ends with 2 rows deleted and 3 moved. With
  the old `(date, scheduleType)` key the case fails: 3 deleted, 2 moved, and
  the loser's per-ride OPERATING row is gone (PAR-256).
- **Schedule dedup** (`test/e2e/schedule-dedup.e2e-spec.ts`): a day with
  opening hours, a gap-filled UNKNOWN row, a ride stated twice and a ride with
  two statuses keeps the hours and one row per ride. A second run deletes 0
  rows, and the per-park cleanup leaves the other park as it was. With the
  ride left out of the phase 1 key the case fails. Phase 2 over a filled
  table of 262 800 rows (about twice production) takes well under a second
  (PAR-277).
- **A merged ride** (PAR-240): review marks for the merge pair, for a third
  ride, for a pair the winner already has a verdict on, and a `not_retired`
  mark on each side, plus a colliding and a non-colliding row in each of the
  other three tables. It runs with the loser's uuid above and below the
  winner's. The merge commits, the single marks of both sides survive, and
  no snapshot is left orphaned.
