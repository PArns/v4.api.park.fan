### Changed — the display-consistency check reads park.fan's relays, runs twice a day and counts what it could not read

Three of its pairs could not fail. Since PAR-1380 a tip is kept under the day's level, so the stamp of
a served tip always equals the one it would get now, and the calendar against the tip's stamp and
against its own `predictedCrowdLevel` compared one calendar read with itself. The test named after
Phantasialand's tip of 2026-11-17 passed only because it mocked `servedVerdicts` into an answer the
method cannot give. The pairs, the surfaces `calendar_predicted`, `parky_tip` and `parky_tip_served`,
and `ParkyTipService.servedVerdicts` are gone.

Both contradictions visitors reported lived in park.fan's copies at Vercel, Cloudflare and the browser,
which the check never read. It now asks park.fan's calendar relay for each month the checked days fall
in, as the calendar grid does, and its best-days relay, as „Prognose heute" does, and compares the
calendar relay with the API's calendar and with the best-days relay beside it on the page. Each relay
value carries the copy's `age`, `date` and cache status, so a mismatch says how old the copy was. A
relay that times out, answers with a Cloudflare challenge or a status other than 200 is a failure,
never a mismatch. Two or three requests a park; the tip relay is not read, since a miss there costs a
model call. park.fan's Cloudflare needs a skip rule for the two paths from the API server
(`User-Agent: api.park.fan-display-consistency`).

The check ran at 09:40 UTC only, after the morning warmup, when every copy agrees. It now also runs at
23:40 UTC, after midnight in Europe, when today has moved on under the evening's copies. Its log line
counted mismatches only, so a run in which every read failed logged the success line; it now names the
parks with unreadable surfaces too, and a run that checked no park. The summary carries `failures`.
