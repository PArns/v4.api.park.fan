### Added — toilets and drinking water from OpenStreetMap, behind `FACILITIES_ENABLED`

`GET /v1/parks/{…}/{park}/facilities` serves a park's toilets and drinking water from
OpenStreetMap with the credit and the ODbL link in the payload
([facilities](frontend/facilities.md)): an open route without a key, because the ODbL allows no
added terms, and a 404 until `FACILITIES_ENABLED` is `true` (default `false`). Only a park an
editor approved serves rows; every other answers `available: false`.

The import is a job on the new `facilities` queue that only the admin starts, for one park or for
all (`POST /v1/admin/facilities/import-all`): park after park with ten seconds in between, a
refused Overpass query sent again after 15, 30, 60 and 120 seconds, the place kept across a
deploy, and a later start taking only what did not go through. A full run is about 420 requests
against the instance's limit of about 10,000 a day. Each park keeps how its last run ended
(`ok`, `no_outline`, `failed` with the reason); a park whose outline carries no matching name is
listed as such and never guessed. `GET /v1/admin/facilities` lists every park with state and
counts, `POST …/approve-all` approves the parks with at least three visible points that all lie
inside the outline, with a dry run first. A re-import is idempotent, deletes what vanished from
OSM, keeps a hidden point hidden, and puts an approved park back to review when it brings a point
nobody has seen. Two new tables, `park_facilities_osm` (OSM-derived rows only, which keeps the
ODbL on that table and off the rest) and `park_facility_imports`.

- Switched on: `FACILITIES_ENABLED` defaults to `true` in the production compose file (the owner's decision, 25 Nov 2026); a park still shows nothing until its import is approved.
