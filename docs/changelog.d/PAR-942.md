### Fixed — ingestion audit: parks east of UTC, live-hours fallback, long outages, reconciliation on a Redis error, blocking KEYS

- **Park status east of UTC.** `getBatchParkStatus` loaded schedule rows up to
  the server's `CURRENT_DATE` (UTC), but `date` is park-local: Universal Studios
  Japan opens 08:00 JST on day D, which is 23:00Z on D-1, so D's row was not
  loaded and the park read CLOSED for its first hour. The window is now ±1 day,
  as `schedule-window.sql.ts` documents.
- **Fallback hours never wrote.** The live-data fallback in the wait-times sync
  and the Wartezeiten opening-times sync only wrote hours when today had no
  schedule row at all — but `fillScheduleGaps` writes an UNKNOWN placeholder for
  today, so the fallback never fired. Both now count only decisive rows
  (`OPERATING`/`CLOSED`, `isDecisiveScheduleRow`); `saveScheduleData` already
  removes the placeholder for a date it writes.
- **Long outages counted as zero.** `downtime:status` / `downtime:start` lived
  one hour, while a ride that stays DOWN only writes a new row at the ~65-minute
  heartbeat, so the keys expired before the recovery and the outage added
  nothing. TTLs are two hours and the start key is refreshed while the ride
  stays down; a start dated an earlier park-local day is ignored, so last
  night's close is not counted as downtime.
- **Reconciliation on a Redis error.** A failed last-seen `MGET` was read as
  "never seen", which closes every missing ride of the park. It now closes
  nothing and logs a warning.
- **No more `KEYS`.** Park cache invalidation, the schedule and calendar-month
  evictions in `ParksService` and the crowd-level eviction after a baseline save
  walked the keyspace with the blocking `KEYS`. They now use the SCAN-based
  `deleteKeysByPatterns`, moved from `src/admin/` to `src/common/cache/`.
- A failed park in the wait-times sync is logged at warn with its error, except
  "No live data available", which the orchestrator already reports per source.
