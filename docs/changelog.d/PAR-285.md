### Fixed — a cached schedule row reports its own day again, west of Greenwich too

`schedule_entries.date` is a DATE column and TypeORM hands it back as a
`"YYYY-MM-DD"` string that already names the day. Five cache branches in
`ParksService` rebuilt it with `new Date(...)` on the way out of Redis, which is
midnight UTC — and `ParkIntegrationService` formats that in the park's own
timezone to pick today's row out of a window running from two days back to
seventeen days ahead. Measured on 2026-09-16:
`2026-09-16` reads back as `2026-09-15` in `America/Los_Angeles` and
`America/New_York`, and correctly in `Europe/London`, `Europe/Berlin`,
`Asia/Tokyo` and `Pacific/Auckland`.

Shifting every row back by a day does not leave the lookup empty — it hands back
the **next** row. With the park-local day 2026-09-16 in `America/Los_Angeles`,
the match is the row dated 2026-09-17, and tomorrow's schedule then decided the
park's status, its rope-drop window and its closing time. Only at the edge of the
published schedule, where no later row exists, did the lookup find nothing at
all.

The asymmetry is why it lasted. A cache **miss** passed the string straight
through and behaved correctly, so the bug only existed with a warm cache and a
cold-start reproduction showed nothing. The write side was never wrong, so
entries already in Redis need no eviction.

`cachedScheduleDay` now reads the day back the way the database hands it out, in
all five branches: `getTodaySchedule`, `getNextSchedule`, both halves of
`getBatchSchedules` and `getUpcomingSchedule`. Only a string can name a day — a
`Date` never reaches the cache as one, because `JSON.stringify` writes it as an
ISO string — and a value that names no day is treated as a cache miss and
rebuilt from the database, which is the rule `safeJsonParse` already states one
level up. Coercing it instead would be the same bug in a second costume:
`new Date(null)`, `new Date(0)` and `new Date(false)` are the epoch rather than
`NaN`, so an absent day would have become 1970-01-01 without a word.

The same rule has been in `ScheduleItemDto.fromEntity` all along, which is why
the API payload was right on both paths while this internal comparison was not.
