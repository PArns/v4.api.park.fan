### Fixed — the two e2e specs that were red on main were testing states their fixtures no longer set up

`pnpm test:e2e` stood at 2 failed, 120 passed on `main`, and both failures were
fixtures that had fallen behind rules the code grew after them. Neither
assertion was wrong, and neither is changed here.

`park-merge` asserts that `repairDuplicates` merges a ghost park away. Since
PAR-262 (#322) that path merges a pair sharing a Queue-Times id only where
`ParkValidatorService.findDuplicates` also calls the pair safe, and `safe` is
`sharedEntityId && nameSimilarity >= 0.95`. The fixture's two parks were named
`winner-park` and `ghost-park`, which score **0.4211**, so the verdict lookup
missed, the loop skipped the pair, and no merge ran at all — the ghost park was
still there because nothing had touched it. The two rows now carry one name, as
one real park read by two feeds does, and keep distinct slugs.

`park-analytics` asserts that `analytics.occupancy` is present on a closed park.
The fixture seeds a park and three attractions and no `queue_data`, so the park
has never reported anything, and `ParkIntegrationService` drops `occupancy`,
`percentiles` and the wait statistics on a park silent for
`PARK_FEED_SILENT_DAYS` rather than publish a verdict about it. One observed
reading, two days old, now says which of the two parks the fixture means: old
enough to sit outside the six-hour live-status window, so the operating counts
the other assertions read do not move.

The merge spec also gained `expectPairIsMergeable`, which asserts the verdict
before calling `repairDuplicates`. The gate had been able to disable the whole
test silently; now a threshold change fails on the sentence stating the
precondition instead of on a count 200 lines below it. Counter-checked one
change at a time: restoring either old fixture puts back exactly its own
failure, and the merge one fails at the new precondition rather than at the
ghost-park count.
