### Performance — the 15-minute prediction dedupe stops reaching across three chunks

Before every prediction run `MLService.deduplicatePredictions` deletes the
park's future rows, and that DELETE carries a `createdAt` predicate so
TimescaleDB can exclude chunks — `createdAt` is the hypertable's partition key.
The predicate was `createdAt >= now() - 13 days`, a width nothing had derived:
at 7 days per chunk it spanned three of them, ~96 times a day for hourly plus
the nightly daily run.

It is now 72h. An hourly run writes slots `[T, T+48h]` from its own
`createdAt = T`, so a row created before `now - 48h` cannot hold a single
future slot the run would want to overwrite — there was never anything to
delete out there. The remaining 24h is slack for a late run and for clock skew;
daily rows are rewritten nightly, so the same window covers two missed nights.
Rows older than the window that still hold a future target are not served
(`getStoredPredictions` requires `createdAt >= now-30min` for hourly and
`>= now-26h` for daily) and the nightly `cleanup-old` job still removes them.

This does not stop the churn behind the 22 GB of chunk indexes on 4 GB of heap
(DB audit 2026-10-12, finding 4a): 94 % of inserted rows are still deleted again
by the next run. Measured on production between the 21:00 and 21:15 runs,
54.8 % of the 3 603 overlapping future slots came back byte-identical (88.9 %
for `predictedWaitTime` alone, `confidence` being the column that moves), so a
diff-write would leave about half the row versions unwritten — but only
together with a generation heartbeat, because a row left in place keeps its old
`createdAt` and would fall out of the 30-minute serving window. That is PAR-874's
remaining work.
