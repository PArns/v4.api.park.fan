### Performance — the 15-minute prediction dedupe stops reaching across three chunks

Before every prediction run `MLService.deduplicatePredictions` deletes the
park's future rows, and that DELETE carries a `createdAt` predicate so
TimescaleDB can exclude chunks — `createdAt` is the hypertable's partition key.
The predicate was `createdAt >= now() - 13 days`, a width nothing had derived:
at 7 days per chunk it spanned three of them, ~96 times a day for hourly plus
the nightly daily run.

It is now derived per prediction type: **72h for hourly, 8 days for daily**.
An hourly run writes slots `[T, T+48h]` from its own `createdAt = T`, so a row
created before `now - 48h` cannot hold a single future slot the run would want
to overwrite — there was never anything to delete out there; the remaining 24h
is slack for clock skew. Daily gets more because its run is skipped for a park
that is closed and had no ride activity, so an off-season or weekend-only park
can go 4-5 days between runs, and a 72h window would leave the previous
cohort's rows for targets inside `[now, now+60d]` undeleted. One wider DELETE
per night is not what this finding is about — the ~96 hourly runs a day are.
Rows older than the window that still hold a future target are not served
(readers are bounded at `now - 50h` for hourly and `now - 26h` for daily, see
below) and the nightly `cleanup-old` job still removes them.

### Performance — hourly predictions are no longer rewritten when they did not change

The narrower window above does not stop the churn behind the 22 GB of chunk
indexes on 4 GB of heap (DB audit 2026-10-12, finding 4a): `generate-hourly`
still deleted every future hourly row of a park every 15 minutes and inserted
the whole 48-hour horizon again — ~25 M inserts and as many deletes a day,
94 % of the written rows deleted again by the next run, chunk primary keys at
15–25× their natural size (8.5 GB instead of ~0.3 GB) and half of all
checkpoints forced by WAL volume.

The hourly path now diff-writes: it reads the park's stored future slots,
compares them with the new run on every served column, inserts only the
changed and new slots, and deletes only their superseded rows and the slots the
run no longer predicts. Measured on production over consecutive runs, 55–80 %
of the overlapping future slots came back byte-identical (88.9 % for
`predictedWaitTime` alone, `confidence` being the column that moves), so that
share of the inserts and deletes disappears. The table cannot use
`ON CONFLICT` for this: as a hypertable on `createdAt` it cannot carry a unique
key on the slot.

Because an unchanged row keeps the `createdAt` of the run that last changed it,
freshness moved from the row to a per-ride Redis marker
(`ml:hourly-fresh:{attractionId}`, 30 min); the old "a row from the last 30
minutes" test still counts, which carries the deploy window itself and, after
that, any ride that had a changed slot in the last 30 minutes. A ride whose
curve sits unchanged writes no row at all, so hourly serving now does depend on
the marker being there.
The hourly read paths now bound `createdAt` by the 50-hour horizon and serve one
row per slot, the newest.

`deduplicatePredictions` is daily-only from here on — the hourly generator no
longer calls it. See docs/database/schema.md, "Write path (PAR-874)".
