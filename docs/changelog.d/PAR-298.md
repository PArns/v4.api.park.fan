### Fixed — a park whose wait times are unknowable stops reporting Ø 0 minutes and a "typical" crowd

PAR-192 withheld three claims for a park with no readable source or a feed
silent for thirty days — the crowd tier, the peak hour and the typical-day
distribution — and named the four it left alone. Those four are this change.
`analytics.statistics.avgWaitTime`, `avgWaitToday` and `peakWaitToday` kept the
zeroes a division by the empty set produces, and the whole `occupancy` object
kept 0 % against a 0-minute baseline with `comparisonStatus: "typical"` beside
it, out of `calculateParkOccupancy`'s own no-data exit. At La Ronde, which has
produced no reading since June, that reads as a verdict rather than as the
absence it is.

The three aggregates now read `null` and `analytics.occupancy` is omitted. Which
field gets which shape was decided by what the readers do with it, not by taste:
of the nine places in the frontend that read the three numbers, five already
gate on `> 0` or `!= null` and four print the value, so `null` renders nothing
and breaks nobody. The occupancy numbers are rounded and compared by their
readers — `Math.round(null)` is 0 — so nulling them would have put the wall of
zeroes straight back; absence is also how the line above it already says this
about `percentiles`. `totalAttractions` survives, because the catalog is real.

`ParkOccupancyDto` is therefore optional on `ParkAnalyticsDto`, and the three
statistics fields are `number | null`, each with a description that says what
the absence means.

`/location` and `/v1/favorites` read the same integrated payload and both
re-derived `avgWaitTime` as
`analytics.occupancy?.breakdown?.currentAvgWait || 0`. That `|| 0` turned the
new absence back into a zero one layer above the fix, so both now leave the
field out; it is optional in both DTOs already.

Two surfaces are measured and left for their own issue, as PAR-192 left them:
the park list (`ParkEnrichmentService.mapParkToDto`) serves the same aggregates
with no gate, and it cannot cheaply learn the measured half —
`hasObservedReadingWithin` is one query per park, so a list of 200 needs a batch
variant first.

`park-integration.unknowable-waits.spec.ts` drives `buildIntegratedResponse`
against a curated park (Hansa-Park's slugs, so `liveWaitTimes.available` is
resolved by the real curated list rather than by a mock) and against a readable
park whose feed has been quiet for 31 days. Every case is a pair: the readable
park is seeded identically, open on the same schedule and handed the same zeroed
analytics, and keeps every figure — remove the gate and the two responses become
the same, which is what the assertions catch. The E2E pair in
`scheduled-but-silent-parks.e2e-spec.ts` gets the same assertions one level up.
