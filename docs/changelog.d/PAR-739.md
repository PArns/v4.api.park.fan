### Fixed — the absence clock reads when the feed last listed a row, not when anything last wrote it

`absent_since` dates an absence the children sync has only just noticed, and it
took `updatedAt` for the evidence that the row still existed. That worked only
as long as the sync was the dominant writer of the table. It is an
`@UpdateDateColumn`, so a curation sweep moves it on rows the feed has not
listed in months — PAR-656 closed that for the gate and left it open for the
seed. Measured on 2026-10-12: nine rows in Europa-Park and Walibi Belgium
carried an absence dated from the `indoorOutdoor` sweep of 2026-10-06 rather
than from their last listing on 2026-04-23. Eight were seasonal and protected
anyway; `VAMPIRE` at Walibi Belgium was not, and is retirable from December
instead of June — 167 days late.

The listing now has a column of its own, `attractions.last_listed_at`, written
by the children sync for every row a park's `/children` carried and by nothing
else. `seedAbsenceWindow` measures both of its windows on it: the 72-hour
fresh-listing window that starts the clock today, and the back-dating that
takes the earlier of the listing and the last real reading. Where the column is
still null the seed falls back to `updatedAt`, which is the old behaviour for
exactly the rows that need it — nothing back-fills the column, so a park's rows
get their first value on that park's first successful sync after the deploy,
and a row already absent by then keeps the fallback for good.

### Performance — the children sync stops rewriting every ride it lists

`syncAttraction` wrote `name`, `latitude` and `longitude` to every listed row on
every run without comparing them to what was stored. Measured on 2026-10-13:
721,469 such statements since 2026-06-03 (50.6 s of execution time), 6,706 of
them in the last run alone — and of 434 rows checked against the live feed
across a sample of 12 of the 192 wiki parks, **not one** carried a value the
feed had moved. The same figure from the other side: 97.85 % of all updates to
`attractions` were HOT, which cannot happen on a changed `name`, because that
column sits in six indexes.

The update now carries only the fields the feed actually moved, and the per-row
write that recorded the listing is replaced by one batched statement per park.
Coordinates are compared at the scale the column stores (`numeric(10,7)`): the
wiki publishes full float precision and TypeORM hands a numeric back as a
string, so the obvious `stored !== incoming` would have written every row on
every run and saved nothing.

The number of rows touched per run does not change — `last_listed_at` has to be
set per listed row or it is not a last-seen timestamp. What goes away is 6,706
statements per run and an indexed column in their `SET`.
