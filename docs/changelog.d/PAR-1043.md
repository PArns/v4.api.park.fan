### Added — ml-bench can measure a candidate against what production served

The offline benchmark gains a `served` arm: `mlbench export` reads the archived
served curves (`forecast_archive_curves`, park_hourly + plan_day + the Chronos-free
incumbent, read-only, by origin day), `build` turns them into
`served_curves.parquet`, and the plug-in `served` answers each bench slot with the
value from the bench origin's own archived capture (an origin without one, intraday
08:00 and 20:00, stays unpaired and is counted in `run-*.json`; never a slot the
capture could already see). `run --model served
--pair-with served` + `report --vs served` give every candidate — Chronos-2,
H5, H5 + TFT, the weekday median, persistence — a paired difference against the
served planner and the served live curve, per use case and lead, with the
park-cluster interval, and best-time regret alongside. `python3 -m
mlbench.served_verdicts` turns that into `offline-model-verdicts.json` entries
against `served` (dry run by default). The archive keeps a curve only 14 days
past its target date, so one export covers about two weeks of targets;
`ml-bench/scripts/accumulate-archive-curves.sh` (read-only, through
`scripts/prod-psql.sh`) exports each new origin day into one persistent directory,
to be run weekly from a systemd user timer whose units are in
`docs/ml/ml-bench.md` — not installed yet. The commands, the earliest achievable
verdict runs and the limitation are in that doc. Nothing has been run on
production yet.
