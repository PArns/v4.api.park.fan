### Fixed — a ride both sources report now receives the wiki's readings, not just Queue-Times'

`externalId` is unique globally and source-scoped, so a ride reported by both
upstreams has one row carrying one id — whichever source created it. The wiki's
name match has always claimed such a row, and has always left its `qt-ride-`
id alone, which is right: that id is how the Queue-Times path finds it. But the
wiki id was then recorded nowhere, and `WaitTimesProcessor` resolves a wiki
entity through `themeparks-wiki:<id>` — the mappings plus an `externalId`
fallback that assumes the id is a wiki id. For a `qt-ride-` row that fallback
registers `themeparks-wiki:qt-ride-11272`, a key no `/live` entry carries, so
every wiki reading for the ride was dropped.

The wiki path now writes the mapping, the way the Queue-Times path has written
its own since PAR-311. Measured against production on 2026-10-26: 35 listed
rows in two parks had no wiki mapping, and 30 of them — all of Energylandia,
all created in the 2025-12-24 seed before the park had a `wikiEntityId` — had
no mapping at all, so they carried nothing but `system-reconciliation` CLOSED
for seven days while the wiki published their waits. No row anywhere held a
wiki mapping beside a `qt-ride-` id, which is what says the gap was the normal
state of that branch rather than an outage.
